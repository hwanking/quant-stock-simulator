## 왜 만들었나

같은 날 두 결함을 잡았는데, 둘 다 **계보** 문제였다.

| 결함 | 실제 모습 | 원인 |
|---|---|---|
| 폐기 산식이 여섯 곳에 살아 있었다 | `recommended_buy_price`(적정가 × 안전마진)가 라운드 25에 폐기됐는데 호출부 6곳이 남아 있었다 | 결정은 **주석에 적혔고** 호출부는 절반만 옮겨졌다 |
| 살 수 없는 가격을 사라고 했다 | 화면이 "211,023원 이하로 사라"고 썼는데 그 가격에서도 실행 게이트가 막고 있었다 | 문구가 게이트를 앞질렀다 |

두 결함 모두 *"이 숫자가 어디서 왔나"* 를 기계가 대신 물었으면 더 빨리 잡힌다.
그래서 회귀(`§107`)에서 매번 묻게 만들었다.

## 무엇을 검사하나

### ① 정적 감사 — 소스만 읽는다

| 검사 | 잡는 것 |
|---|---|
| ⒜ 폐기 키 부활 | 표시 경로 10개 파일에서 `recommended_buy_price` 가 라벨 없이 쓰이는가 |
| ⒝ 신규·보유자 혼용 | `entry_stop_price`(신규)와 `stop_loss_price`(보유자)가 이름표 없이 한 줄에 |
| ⒞ 중앙 판정 우회 | 화면이 `four_scores` 에서 진입가를 직접 읽는가 (CORE 를 안 거치고) |
| ⒟ 사전등록 후보 누출 | R55·R57·R66 후보가 운영 코드에 들어갔는가 (8/23 동결) |

**핵심 설계 — 주석은 근거가 못 된다.**
폐기 산식이 여섯 곳에 살아남은 이유가 정확히 *"주석엔 적혀 있었다"* 였다.
주석을 근거로 통과시키면 **검사가 결함을 감싸게 된다.** 그래서
`prose_lines()` 가 ast 로 독스트링·`#` 주석·`<!-- -->` 구간을 먼저 걷어낸다.

라벨로 인정하는 것은 두 가지뿐이다:

- **식별자 이름** — `_value_floor`, `value_ref` (다음 사람이 코드에서 읽는다)
- **사용자에게 실제로 렌더되는 문구** — `"장기 가치 참고선"`, `"오늘의 매수가가 아니다"`

### ② 실행 추적 — 실제 종목을 흘린다

종목 N개를 파이프라인에 통과시켜 `verdict_core.build()` 결과를 만들고,
화면에 나갈 값들의 **출처 키**를 기록한 뒤 정합을 재계산한다.

- 손절 < 진입 < 목표 가 실제로 성립하는가
- 손익비가 `(목표−진입)/(진입−손절)` 과 맞는가 — 다른 엔진의 옛 손익비가
  남아 있으면 여기서 어긋난다 (라운드 30 사고의 자동 탐지)
- 진입가가 축(`price_axes.entry`)에서 왔는가, 폴백에서 왔는가
- 신규 값과 보유자 값이 같은 숫자로 겹치는가

산출물: `data/lineage_audit.json`

## 첫 실행에서 잡은 것

### 진짜 결함 1건 — 적정가 화면이 폐기 산식을 '살 가격'이라 불렀다

`web_app.py` 적정가 구간이 아직 이렇게 쓰고 있었다:

```
권장 매수가 (안전마진 15% 적용)   173,656원 이하
현재 진입 평가                    안전 매수 구간   ← 초록색
```

라운드 25에 실행가 자리에서 폐기하고 37에 배너에서 걷어낸 값인데,
이 화면만 옛 이름으로 남아 있었다. 사용자가 지적한 *"적정가와 매수 기준이
둘 다 '사도 되는 가격'처럼 보인다"* 가 여기서 그대로 재현됐다.

고친 뒤:

```
장기 가치 참고선 (안전마진 15%)   173,656원 이하
장기 가치 대비                    가치 기준 저평가 구간

위 참고선은 장기 가치 기준입니다 — 여기까지 내려와도 매수 신호가
켜지는 것은 아닙니다. 오늘의 실행 진입가는 XXX원 (종합 결론 배너와 같은 값).
```

변수 이름도 `rec_buy` → `_value_ref` 로 옮겼다. **주석에만 적어 두면 다음
사람이 또 실행가로 읽는다** — 실제로 그래서 여섯 곳이 살아남았다.

### 감사 자신의 결함 1건 — 못 잰 것을 통과로 적었다

첫 실행에서 파이프라인 함수 이름이 틀려 10종목 **전부** 스냅샷에 실패했는데,
감사는 `정합 위반 0건 · 전부 통과` 를 찍었다. 재고 있지 않은데 통과라고 쓴
것이다 (CLAUDE.md §3 — 데이터 미수신 ≠ 문제 없음).

고쳤다. 스냅샷 실패는 사유와 함께 **결함으로 올린다.**

### 내가 새로 넣은 회귀 검사도 같은 실수를 했다

§107 에 `'안전 매수 구간' not in web_app.py` 를 넣었더니 **실패했다.** 남아
있던 두 곳은 둘 다 *"옛 이름이 무엇이었나"* 를 설명하는 주석이었다.
감사에는 산문 제거기(`prose_lines`)를 만들어 놓고, 정작 검사는 소스 전체를
문자열로 훑은 것이다. 검사가 감사와 **같은 기준으로 코드를 보게** 고쳤다
(`_la107.code_lines('web_app.py')`).

### 옛 검사 1건 — 정직한 동작을 결함으로 몰고 있었다

`판정 문구에 KOSPI200 포함` 이 실패했다. 원인을 보니 벤치마크 대조는
종목 쪽 성과(`ai_perf`)가 있어야 성립하는데, 유사패턴 표본이 0건이면
`ai_perf` 는 `None` 이고 엔진은 *"표본 부족으로 벤치마크 대조를 산출하지
못했습니다"* 라고 적는다 — §3 그대로의 정직한 동작이다. 검사가 무조건
`KOSPI200` 문자열을 요구하고 있었다.

검사를 현실에 맞췄다. **느슨해지지는 않았다** — 대조가 성립하는데
KOSPI200 이 빠지면 여전히 실패한다.

### 오탐 3건 — 검사를 고쳤지 코드를 고치지 않았다

첫 판에서 `verdict_core.py:13-14`(독스트링의 옛 이름 목록)과
`web_app.py:5250`(라운드 53c 수정 기록 HTML 주석)을 결함이라고 찍었다.
셋 다 산문이다. ast 기반 `prose_lines()` 로 걷어냈다.
