## 2. 왜 초록이었나 — 증분 0 을 실패로 안 만든 이유가 파일마다 다르다

라운드 81 의 증분 요약은 *"계획이 다 찬 날은 0 이 정상이다 — 실패로 만들지 않는다"* 고 적었다. 원장
(`virtual_graded`)에는 맞는 말이다(라운드 213 · 격자가 차면 0). **전방 기록부는 다르다** — 매 거래일
상위 60 을 박제하는 것이 그 파일의 정의(fr-1)라 거래일의 0 은 정상일 수 없다. 한 요약이 성질이 다른
아홉 파일에 같은 규칙을 대고 있었다(R233 의 "같은 이름의 수가 둘이면 단위를 옆에" 와 같은 계열 —
같은 '증분 0' 이 파일마다 다른 뜻이다).

라운드 263 의 실행 기록 검사는 *일일 개선 파이프라인*의 침묵만 잡는다. 라운드 245 의 신선도 검사는
산출물이 **어느 원장에서** 만들어졌나를 본다. **"오늘 아무것도 안 쌓였다"** 를 보는 검사는 없었다.

## 3. 고침 — `scripts/forward_registry_check.py` · 워크플로 맨 뒤

| 판정 | rc |
|---|---:|
| 휴장일 | 0 (판정하지 않는다) |
| 오늘 날짜(`date`) 행 ≥ 1 | 0 (몇 건인지 찍는다) |
| 거래일인데 오늘 행 0 | **1** — 그날 "전방 판정 기록" 단계 로그가 사유를 말한다 |
| 파일 없음 · 못 읽음 | 2 (미측정 · 통과가 아니다) |

- 휴장일 판정은 한 곳(`improvement.case_tracker.is_non_trading_date` · R252). 오늘은 프로세스의 지역
  날짜(워크플로 `TZ=Asia/Seoul` · R222 의 UTC 함정).
- 자리는 **업로드 뒤 · 실행 기록 검사 다음**(R247 · 축적은 인질이 아니다) · `|| true` 없음.
- 원장·경로 파일의 0 은 그대로 둔다 — 그쪽은 0 이 정상일 수 있고, "정상인 0" 과 "멈춘 0" 을 가르는
  기준을 정하면 §2 다. 전방 기록부만 정의상 0 이 불가능하다.
- 로컬 실측(2026-09-11 14:40 · 클라우드 실행 전): `360행 · 날짜 6일 (2026-08-14 ~ 2026-09-07) · 오늘 행
  0건 → 실패`. 오늘 17:00 KST 실행 뒤 main 이 R270+ 이면 통과, 아니면 이 검사가 처음으로 붉어진다.

## 5. 규칙으로 남기는 것

- **'증분 0' 의 뜻은 파일마다 다르다.** 정의상 매일 늘어야 하는 파일은 0 을 실패로, 격자가 찰 수 있는
  파일은 0 을 경고로. 한 요약에 같은 규칙을 대지 않는다.
- **초록불 25개가 쌓은 것 0 을 가릴 수 있다.** `|| true` · `continue-on-error` 뒤에는 실행 기록(R263)
  이나 산출물의 오늘 행(R272)처럼 **값**으로 침묵을 잡는 검사를 맨 뒤에 둔다.
- **외부 자료원 이전은 배포된 코드가 막는다.** 고친 코드가 브랜치에 있어도 main 이 옛 것이면 클라우드는
  매일 0 을 쌓는다 — 만든 것은 실린 것이 아니다(R261).
