# 결과 R341 — 재무 시점 보관을 오늘 시작한다 (2026-09-18)

라운드 336 이 셌다: 이 저장소에 재무 시점 자료가 없고(원장 43칸에 재무 칸 0), 받는 연간 재무는 **재작성된 현재
보고치**라 과거 기준일에 붙이면 누출이다(§1). *"좋은 기업인가"* 를 원장으로 재려면 **그날 알 수 있던 재무**가 날짜와
함께 남아 있어야 하고, 그것은 시작한 날부터만 쌓이며 소급되지 않는다 — 시작한 날부터 12개월이 이 물음이 열리는
시점이다. 늦출수록 손해라 **오늘 시작한다.** 사용자의 *"산식은 그전에 바꿀 게 없나 · 더 기다리는 게 맞나"* 에 대한
답의 실행분이다: 바꿀 산식은 없고, **지금 할 수 있는 것은 재료를 쌓기 시작하는 것**이다.

## 무엇을 · 어디서 · 얼마에

| | |
|---|---|
| 재료 | 라운드 339 가 보관해 둔 `finance/annual` 응답(`bitemporal_engine.ANNUAL_FIN_BY_CODE`) — **추가 네트워크 0** |
| 언제 | 클라우드 전방 판정 기록기(`scripts/forward_recorder.py`)의 **끝** — 그날 정밀분석한 상위 60종목 |
| 어떻게 | `fin_pit.rows_from` → 종목·날짜마다 한 줄(연도 열의 추정 여부 그대로 · 값은 수 · `-` 는 None) · `append_rows` 는 같은 (종목, 날짜)를 한 번만(멱등) |
| 어디 | `.portfolio/fin_pit.jsonl` — 백업 화이트리스트(`backup_research_data.INCLUDE`)와 증분 요약 감시(`snapshot_guard.WATCH`)에 같은 이름 |
| 저장 | 한 줄 ≈ 16항목 × 4개 연도 · 하루 60줄 — 연간 수 MB |
| 실패 | 판정 기록과 무관하게 따로 세어 찍는다 — *"오늘 몫은 못 남겼다"* 고 적는다(§3) |

**범위를 정직하게 적는다** — 전 종목이 아니라 **그날 기록기가 본 60종목**이다. 시점 표가 전 종목이어야 하는
연구(횡단면)는 이 자료로 못 연다. 60종목 × 거래일이 쌓이면 *같은 종목의 재무가 그날 무엇이었나*(추세 · 재작성)
를 셀 수 있다 — 그것이 열리는 첫 물음이다.

## 실측 (2026-09-18 · 이 PC · 임시 경로)

한 종목을 실제 엔진 경로로 풀어 시점 행 1줄(항목 16 · 연도 4 · 2026.12 추정 표시) · append 멱등(두 번째 0줄).
클라우드에서 실제로 쌓이는지는 **다음 실행의 `재무 시점 보관 — 오늘 N줄` 줄**이 증명한다(R259 의 그 문장).

## 바꾸지 않은 것

적정가·점수·판정·게이트 전부 · `info` 의 재무 칸 여섯(§342). 값을 해석하거나 고르는 규칙은 하나도 없다 —
그것은 사전등록의 일이다(§2). 검사 §347(6건).

## 부록 — 클라우드가 증명했다 (2026-09-22 확인)

*"클라우드에서 실제로 쌓이는지는 다음 실행이 증명한다"* 고 적어 두었다. **증명됐다.**

2026-09-21 예약 실행(성공 · 2시간 42분 · 실행 `35615698424`)의 전방 판정 기록 단계:

```
재무 시점 보관 — 오늘 60줄 새로 · 이미 있음 0줄 · 받은 응답 없음 0종목
                 → 누적 60줄 · 종목 60 · 날짜 1 (2026-09-21 ~ 2026-09-21)
```

같은 실행의 증분 요약이 같은 수를 낸다 — `fin_pit.jsonl 0 → 60 (+60)`. 업로드 직전
축소 가드와 §9 zip 감사(평단가·자격증명 0건)를 지나 `data-20260921` 릴리스에 실렸다.
**만든 것이 실린 것까지 확인했다**(라운드 261 의 그 자리).

- *"받은 응답 없음 0종목"* — 엔진이 이미 받는 연간 재무를 그대로 옮기므로 **추가
  네트워크가 0**이라는 말도 함께 확인됐다.
- 날짜는 아직 **1일**이다. 연구가 열리는 시점(12개월)은 그대로다 — 쌓이기 시작한
  것과 잴 수 있는 것은 다르다.
