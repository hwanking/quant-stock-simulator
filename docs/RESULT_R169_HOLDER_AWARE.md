# 라운드 169 — '내 계획'을 걷어내고, 엔진 판단이 보유 여부를 보게 했다

작성 **2026-08-24**

> *"내 계획은 지워버리고, 엔진 판단부터 제대로 되도록 해줘. 지금 보유한
> 상태에서는 더 매수인지 매도인지, 없으면 매수인지. 내 포트폴리오에 대한
> 견해도 관심종목 밑에 적절하게 넣어주면 좋겠어."*

| **166** | 내 계획 + **엔진 판단** | *"내 계획이 아니라 실제로 너가 판단해서"* |

- 화면에서 칸을 없앴다

  처음부터 같다 — *사용자가 적는 칸은 매입가·수량 둘뿐, 엔진 값 칸에는
  입력 위젯이 없다.*

## 2. 엔진 판단이 **보유 여부**를 본다

사용자가 물은 그대로: *"보유한 상태에서는 더 매수인지 매도인지, 없으면
매수인지."*

### 매입가를 적었으면 — 보유자 기준

| 조건 | 판단 |
|---|---|
| 현재가 ≤ **버틸 수 없는 가격**(`hold_stop`) | **정리 검토** |
| 현재가 ≥ **팔 가격 1차**(`hold_trim`) | **일부 정리** |
| 엔진이 '오늘 매수 가능' 이고 현재가 ≤ **목표 매수가** | **추가 매수 가능** |
| 그 사이 | **보유 유지** |

### 안 적었으면 — 신규 매수자 기준 (`bucket` 그대로)

매수 가능 / 눌림목 대기 / 돌파 대기 / 과열·거래량·국면 대기 / 괴리 과다 /
표본 대기 / 데이터 부족 / 사지 않음

### ⚠️ 새 판정을 짓지 않았다

`ui_kit.watch_action()` 한 곳에서만 나오고, 그 함수가 하는 일은
**엔진이 이미 발표한 가격선과 현재가를 견주어 한 줄로 다시 말하는 것**
뿐이다. 새 문턱을 만들면 §2 위반, 판정을 다시 지으면 §4 위반이다.

검사가 그것을 **값으로** 잡는다 — `watch_action` 본문의 **비교에 쓰이는
숫자 리터럴**이 하나라도 있으면 실패한다(§204 ⓒ).

> 처음에 숫자 리터럴을 전부 셌다가 `bucket[:7]`(문자열 자르기)에 걸렸다.
> **문턱이란 비교에 쓰이는 숫자**이므로 `Compare` 노드 안만 보도록 좁혔다 —
> 검사가 무엇을 재는지 정확히 적는다.

### 신규 매수자 값과 보유자 값을 섞지 않는다 (§4 · 라운드 30 사고)

- 보유 판단은 `snap_hold_stop`·`snap_hold_trim` **만**
- 미보유 판단은 `snap_bucket`·`snap_buy` **만**

검사가 둘을 따로 준다: *"보유 판단은 신규 매수자 값 없이도 난다"* ·
*"미보유 판단은 보유자 값 없이도 난다"*.

보유자 값을 담을 키를 새로 만들었다 — `snap_hold_trim` · `snap_hold_stop`.
세 저장 경로(라운드 141·142·166)가 전부 `CORE` 에서 그대로 담는다.

## 3. 내 포트폴리오 견해 (관심종목 밑)

**하는 일** — 위 표가 이미 낸 판단을 **세기만** 한다. 판단을 두 번
계산하지 않는다(§4 — 검사가 `watch_action` 호출이 **1회**인지 본다).

- 보유 종목 수 · 평가금액 · 평가손익 · **가장 큰 종목 비중**
- 보유 중 / 안 산 것 각각의 **판단 분포** (종목 이름까지)
- **못 잰 것을 밝힌다** (§3) — 현재가 미수신 · 엔진 값 없음

**하지 않는 일** — 비중을 얼마로 하라거나 무엇을 사라고 하지 않는다.
그리고 그 자리에 이 사실을 함께 적는다:

> 이 엔진의 매수 신호에는 **비용 차감 뒤 실전에서 재현되는 우위가 확인되지
> 않았습니다** (원장 184,759건 전수 — 블라인드 적중 50.4% vs 본전 63.7% ·
> 라운드 159·168).

§9 가 요구하는 그대로다 — 성과를 좋게 보이게 쓰지 않는다.

## 3b. 화면에서 보고 하나 더 고쳤다 — "보유 유지 13종목"

붙이고 화면을 열었더니 보유 13종목이 **전부 '보유 유지'** 로 나왔다.

그건 판단이 아니었다. `snap_hold_stop`·`snap_hold_trim` 이 **이번 라운드에
새로 만든 키**라 아직 아무 종목에도 안 찍혀 있었고, 판단 함수가 "정리도
아니고 추가 매수도 아니니 보유 유지"라는 **소거법**으로 떨어진 것이다.

**못 잰 것을 판단으로 만든 것**이라 §3 위반이다. 고쳤다 —
보유자 가격선이 **하나도 없으면** `보유 기준 미산출`이라 적고 판단하지
않는다. 그리고 채우기 버튼이 그 종목들도 대상으로 잡게 넓혔다
(매입가는 있는데 hold 값이 없는 경우).

검사가 그것을 값으로 잡는다:

```
watch_action({'paid': 10000, 'snap_bucket': '추천 제외'}, 10500)
  → '보유 기준 미산출'          (가격선이 하나도 없다)
watch_action({'paid': 10000, 'snap_hold_stop': 8000}, 10500)
  → '보유 유지' · "버틸 수 없는 가격(8,000원) 위입니다"
```

> 회귀는 초록불이었다. **화면을 열어야 나오는 결함**이 또 나왔다 (§6).

### 그리고 그 뒤에 **더 큰 것**이 있었다 — 같은 실수를 두 번 했다

'보유 기준 미산출'이 왜 그렇게 많은지 파 보니, 채우기 버튼이 이렇게
부르고 있었다.

```python
_co166 = _vc166.build(_snp166)        # ← 스냅샷을 통째로
```

`verdict_core.build()` 의 첫 인자는 **`four_scores`** 다. 스냅샷을 넘기면
안에서 읽는 키가 **전부 None** 이 되고, 그래서 채운 종목이 죄다
`bucket='데이터 부족'` 에 보유자 값이 비었다. **못 낸 게 아니라 잘못
물어본 것**이다.

**라운드 167 에서 겪은 것과 정확히 같은 모양이다** — 그때는
`evaluate_valuation_metric` 에 원본 일봉 프레임을 넘겨 남의 적정가를
받았다. 한 라운드 만에 같은 실수를 반복했다.

화면(`web_app.py:5816`)이 부르는 방식 그대로 맞췄다:

```python
_co166 = _vc166.build(_fs166, verdict=_vd166,
                      price_axes=_fs166.get('price_axes'),
                      next_action=_na166,
                      realtime_price=_fs166.get('current_price'))
```

고친 뒤 실측:

| 종목 | 상태 | 판단 |
|---|---|---|
| 다날 (미보유) | bucket '눌림목 매수 대기' | **눌림목 대기** |
| 한화투자증권 (평단 4,760 · 현재 4,850) | hold 5,172 / 4,390 | **보유 유지** — *"버틸 수 없는 가격과 팔 가격 1차 사이입니다"* |
| 광주신세계 (평단 40,703 · 현재 36,600) | hold 38,070 / 34,500 | **보유 유지** |

**두 번 했으니 검사로 못 박았다** (§204 ⓕ): `verdict_core.build()` 의 첫
인자가 이름에 `snap`/`snp` 를 담고 있으면 실패한다. 심어서 잡히는지도
확인했다.

## 4. 검사 (§204)

- **값으로** 잰다: 같은 종목이 매입가 유무로 판단이 달라지는가 (6가지)
- 아무것도 안 잰 종목은 판단하지 않는가 (§3)
- 현재가를 못 받으면 보유 기준으로 넘어가지 않는가
- 보유·미보유 판단이 **서로의 값 없이도** 나는가 (§4)
- `watch_action` 이 **비교에 쓰는 숫자**를 만들지 않는가 (§2)
- '내 계획'이 화면·저장 어디에도 남지 않았는가
- 견해가 판단을 **다시 계산하지 않는가** (호출 1회)
- 못 잰 것을 밝히는가 · 우위 없음을 함께 적는가
