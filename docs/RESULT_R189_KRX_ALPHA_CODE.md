# R189 — 진짜 KRX 문자코드를 남의 코드로 바꾸고 있었다

**날짜**: 2026-08-31 · **트리거**: 라운드 188 전수 감사가 남긴 백로그 중
가장 위험한 것(사용자 자료에 닿는 경로)

## 무엇이 있었나

보유종목 입력(붙여넣기·OCR·CSV)의 코드 판별이 이렇게 돼 있었다:

```python
# ② 섞인 글자가 전부 '숫자로 오해받는 글자' 면 OCR 오독으로 보고 되돌린다.
if all(c in _OCR_DIGIT_LOOKALIKE for c in others):
    fixed = repair_ocr_code(up)     # D→0, Z→2, G→6, A→4, S→5, T→7, B→8
```

그런데 **KRX 가 실제로 쓰는 글자가 그 표에 다 들어 있다.** 실측
(`data/etf_taxonomy_r170.json` 1,161종목 · 문자 포함 296종목):

```
0000Z0  RISE AI TOP10        → 000020   ← 동화약품
0004G0  1Q 미국채TOP30       → 000460   ← 실재 상장 종목
0005D0  SOL 반도체소재       → 000500   ← 가온전선
0022T0  SOL 커버드콜         → 002270   ← 빙그레
… 296개 중 114개 (38.5%)
```

`stock_code.py:20` 이 *"숫자만 뽑아 zfill 하는 방식이라 **다른 종목의
코드를 만들어 냈다**"* 고 적어 둔 라운드 165 의 결함이, **표기만 달리해
(문자→숫자 치환)** 여기 살아 있었다. 그리고 이건 **보유종목 입력**
경로라 남의 종목 값이 내 줄에 붙는다.

§202 검사가 못 본 이유도 같다 — 그 검사는 `filter(str.isdigit)` ·
`re.sub(r'\D')` **두 표기만** 금지한다. 세 번째 표기였다.

## 어떻게 갈랐나 — 감이 아니라 실측

문자코드 296개의 **모양**을 쟀다(`_probe/r189_shape.py`):

| 잰 것 | 결과 |
|---|---|
| 문자가 나오는 자리 | **전부 index 4** (5번째 자리) · 296/296 |
| 한 코드의 문자 개수 | **전부 1개** · 296/296 |
| 첫 글자 | **전부 `0`** · 296/296 |
| 쓰이는 글자 | `ABCDEFGHJKLMNPRSTVWXYZ` — **I·O·Q·U 가 한 번도 없다** |

마지막 줄이 결정적이다. KRX 가 빼 놓은 넷이 **정확히 숫자와 헷갈리는
글자**다(I→1 · O→0 · Q→0). 즉 실재 코드 집합과 오독 글자 집합이
**겹치지 않는다** — 오독 교정을 잃지 않고 진짜 코드를 살릴 수 있다.

## 고침

판별식은 `stock_code.looks_like_krx_alpha()` **한 곳**에 둔다 — 라운드
164 가 *"규칙은 한 곳에만"* 이라며 정한 자리다. `portfolio` 는 그것을
부르고, 실재 코드 모양이면 **손대지 않고** 그대로 돌려준다.

**실측 (고친 뒤)**

| | 종전 | 지금 |
|---|---|---|
| 실재 문자코드 296개 | **114개(38.5%) 손상** | **0개** |
| OCR 오독 `0O0660` | `000660` 교정 | `000660` 교정 (유지) |
| `OO5930` · `00S93O` | 교정 | 교정 (유지) |
| 종목명 `ABCDEF` | 코드 아님 | 코드 아님 (유지) |

과차단이 아니다 — 오독 교정은 한 건도 잃지 않았다.

**곁들여**: `read_code_cell(tok)[0]` 로 **교정 표시를 버리던** 세 번째
경로에 경고를 살렸다. 같은 파일의 다른 두 경로(`:1333` · `:1544`)는
*"종목코드 인식 교정 … (확인 필요)"* 를 남기는데 이 자리만 조용히
바뀐 코드를 보유 줄에 붙였다.

## 함께 고친 죽은 경로 셋 (R188 감사 후속)

- **`_KEEP` 폴백이 키 이름 불일치로 통째로 죽어 있었다.** `_keep()` 은
  `'t_ref'`·`'rho'` 로 저장하는데 폴백은 `'t_ref_date'`·`'rho_cutoff'`
  로 찾았다. 그래서 사이드바 4단계를 접는 순간 사용자가 고른 기준일·rho
  가 **조용히 기본값으로 되돌아갔다** — 주석이 약속한 *"접었다 펼쳐도
  유지된다"* 가 거짓이었다. `_KEEP_ALIAS` 로 잇는다.
- **CSV·Excel 가져오기가 시장을 안 붙였다.** `_resolve_market` 을 바로
  위에서 정의해 놓고 `resolve_market=None` 을 넘겨, **모든 종목의 시장을
  미상으로** 만들고 행마다 경고를 뿌렸다. 붙여넣기 경로(`:4445`)는
  제대로 넘기고 있어 두 경로가 달랐다.
- **진행 표시가 통째로 죽어 있었다.** `scan_busy` · `scan_stage` ·
  `_sb_busy` 를 **읽는 곳만 있고 쓰는 곳이 저장소 어디에도 없었다.**
  그래서 아코디언의 '처리 중 ●' 과 상단 띠의 '지금 돌고 있는 작업' 이
  한 번도 안 떴다. 켜고, **끄는 길은 `_scan_done()` 하나로** 모았다
  (조기 반환에서 표시가 영원히 남지 않게).

## 검사 (§219)

판별식이 `stock_code` 한 곳에 있는지 · `portfolio` 가 규칙을 베끼지
않았는지 · 실재 코드/오독을 **값으로** 가르는지 · **실재 문자코드
296개 전수**가 안 바뀌는지(그리고 몇 개를 봤는지) · 실측 모양이 여전히
100% 를 덮는지(어긋나면 규칙을 다시 재라는 뜻) · 오독 교정을 잃지
않았는지 · 교정 표시를 버리지 않는지 · 죽은 경로 셋 · 옛 표기 심기.

## 검사가 내 수정을 잡았다 — 그리고 그 검사가 좁았다

회귀가 §201 ⓜ *"쓰기만 하고 아무도 안 읽는 세션 키가 없다"* 로 실패했다.
`scan_busy` · `scan_stage` 를 죽은 키로 지목한 것이다.

먼저 **검사가 옳은지부터 봤다.** 두 키를 읽는 곳은 `live_ticker.py:51-55`
이고 `web_app.py:630` 이 `session=st.session_state` 를 넘긴다 — 읽기는
실재한다. 그런데 **검사는 `web_app.py` 안만 파싱하고 있었다.** 라운드
120e·164·165 가 세 번 겪은 **'유도가 좁았다'** 와 같은 모양이다.

고침: 쓰기는 `web_app` 에서 세되 **읽기는 유도된 전 모듈**(`_reach201`)
에서 센다 — 목록을 손으로 적지 않는다. 그리고 **몇 개 모듈을 봤는지**를
값으로 잠근다(라운드 120e 가 *"개수를 찍으라"* 한 이유). 실측: 유도 37개
중 **36개 모듈**을 읽기 집계에 넣었고, 죽은 키 0건, **심은 죽은 키는
여전히 잡힌다**.

문턱을 내린 것이 아니다 — 읽기를 더 넓게 세므로 **web_app 안에서는 종전
그대로 엄격**하고, 잘못 잡던 교차 모듈 경우만 바로잡았다.
