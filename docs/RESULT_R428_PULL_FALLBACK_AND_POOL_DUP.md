## 1. 밤 되받기 — "돌았다"가 아니라 "받았다"로 본다

라운드 420 이 저녁 작업(`scripts/nightly_local.py`)의 첫 단계로 클라우드 되받기를 넣었다. 저녁 작업 기록을 열어 보니
그 단계가 **종료 1** 이었다:

```
클라우드 되받기 — 종료 1 · 0초 · To get started with GitHub CLI, please run:  gh auth login | … | 내려받을 스냅샷이 없다.
```

나머지 세 단계(추적 동결 · 관심종목 재측정 · PROOF 성적표)는 성공이라 작업 전체가 "돌았다"로 보였다. **대화형 셸에서는
gh 가 로그인돼 있고 같은 명령이 된다** — 작업 스케줄러가 띄운 환경에서만 '로그인 안 됨'이다.

### 첫 가설은 틀렸다

대화형 셸에서 환경 변수를 하나씩 빼 보니 **`APPDATA` 하나만** 빠져도 같은 증상이 나왔다. 그래서 `gh_env()` 로 비면 메우게
했고 예약 실행을 다시 띄웠다 — **똑같이 실패했고, 메웠다는 표시가 안 붙었다**(그 환경에도 `APPDATA` 는 있었다). 증상을
재현한 것이지 원인을 재현한 것이 아니었다. 진짜 원인은 **못 쟀다**(키링에 못 닿는 것으로 추정할 뿐이다). 그 함수의
설명을 *"그 가설은 틀렸다"* 로 고쳐 두었다 — 틀린 설명을 코드에 남기지 않는다.

### 고침 — 공개 저장소라 인증 없이 받는다

저장소가 공개라 릴리스 목록과 자산은 인증 없는 HTTPS 로 읽힌다. gh 가 실패하면:

- 목록: `https://api.github.com/repos/{owner}/{name}/releases`(쪽 넘김) → `rows_from_releases()` — gh 의 jq 식과 **같은 규칙**의
  순수 함수(`data-` 태그 · `research_data_` 자산이 있는 릴리스만 · 시각은 그 자산들의 최신 · 이름은 가장 늦게 갱신된 것)
- 파일: `https://github.com/{owner}/{name}/releases/download/{태그}/{이름}` → 임시 이름 → 다 받으면 바꿔 끼움(같은 INBOX · 같은 이름)
- 저장소 이름: `.git/config` 의 origin 에서 먼저(gh·네트워크 불필요) · 못 읽으면 gh
- gh 실행 파일을 못 찾으면 예외로 죽지 않고 종료 127 과 사유
- 두 길이 다 실패하면 두 사유를 찍고 멈춘다 — 목록을 지어내지 않는다(§3)

같은 시각 두 길의 목록이 **31개로 같았다**(태그·시각·이름 전부). 그리고 예약 실행으로 다시 띄웠다:

```
[10-06 08:00:00] 클라우드 되받기 — 종료 0 · 15초 · … 되받기 끝 · data-20261005 · 원장 257,130 → 257,530 · 덮어씀 80 · 물러섬 0 · zip 지움 7
[10-06 08:00:33] 끝 · 가장 나쁜 종료 코드 0
```

⚠️ 그 실행이 공개 HTTPS 길로 받았다는 것은 **차례로 추론한 것**이다(바로 앞 예약 실행은 같은 환경에서 gh 로 실패했고,
그 사이에 바뀐 것은 이 물러섬뿐이다). 저녁 작업 기록은 단계 출력의 끝부분만 남겨 그 줄 자체는 안 보였다.

## 2. 클라우드 오염 점검이 붉어졌다 — 그것은 제 일을 했다

10-05 클라우드 실행의 꼬리 검사(`contamination_audit.py --verify`)가 실패했다:

```
0 이어야 하는 수가 0 이 아니다: ['ledger.dup=2500 (알려진 옛 2,499 초과)', 'virtual_predictions.dup=288 (알려진 옛 287 초과)']
```

받아 둔 스냅샷 셋으로 중복 열쇠(종목코드 6자리, 기준일)를 대 보니 **10-03 → 10-06 사이에 정확히 1묶음**이 새로 생겼다.
두 행은 원장에서 **나란히** 있었다(한 실행이 둘 다 썼다) — 같은 종목의 `.KQ`(main) 와 `.KS`(holdout).

### 라운드 390 의 고침이 닿지 않은 자리

라운드 390 은 완료 판정 열쇠에서 시장 접미사를 뗐다 — 이미 만든 케이스를 **다음 실행이** 다시 만들지 않는다. 그런데
**한 실행 안에서는** 두 변이가 둘 다 '아직 안 만든 것'이라 같은 (코드, 기준일)이 계획에 두 번 들어갔다. 원인은 계획 목록이다:

| 어디서 | 무엇이 |
|---|---|
| 고정 목록 안 | 같은 코드가 홀드아웃 목록에 두 접미사로 한 번 든다 |
| 유니버스 덧붙이기 | 기존 목록을 **전체 티커 문자열**로 빼서, 고정 목록의 `.KS` 종목이 `.KQ` 로 다시 들어온다 |

2026-10-06 실측(원장 257,530행): 중복 묶음 **2,500 이 전부 이 25개 코드**다 — 고정 목록 안의 겹침 **376** · 고정 목록 ↔
덧붙인 변이 **2,124** · 둘 다 목록 밖 0. 라운드 390 이 원인을 *"접미사가 바뀌어서"* 라고 적었는데, 더 정확히는 **계획
목록이 같은 종목을 두 이름으로 들고 있었다**. 그 열쇠 고침은 실행 사이를 막았고, 실행 안은 열려 있었다.

### 고침

- `calibration_lab.dedupe_by_code(목록)` — 같은 6자리 코드는 **처음 것만** 남긴다(차례 그대로 → 고정 목록이 먼저 ·
  위 주석의 *"기존 종목이 먼저"* 그대로). 유니버스 덧붙이기 **뒤**, 샤드 가르기 **앞**에서 한 번 — 가른 뒤에 거르면 두 변이가
  다른 워커로 가서 서로를 못 본다. 뺀 수를 찍는다.
- 계획 루프에 **이번 실행의 계획 집합** — 같은 열쇠(`scale_key`)를 완료 집합과 계획 집합에 같이 묻는다. 목록을 걸러도
  한 번 더 막는다(목록이 어떻게 생기든 성립하는 불변식).
- 오염 점검의 알려진 수를 2,499 → **2,500** · 287 → **288** 로 옮겼다. **그 1행은 지우지 않는다**(라운드 197) — 통계에서는
  `ledger_view.stat_rows` 가 이미 뺀다. 또 늘면 그것은 새 누수다. 알려진 수를 글자로 박고 있던 회귀 한 줄은 표에서 읽게 했다.

**이 변경은 연구 표본을 바꾸지 않는다** — 빠지는 것은 같은 종목·같은 날의 두 번째 복사본뿐이다. 홀드아웃 안의 겹침은 두
변이가 둘 다 홀드아웃이라 갈래도 안 바뀐다.

### 덤 — 종목 홀드아웃은 종목코드로는 겹쳐 있었다

라운드 291 이 *"`main ∩ holdout` = 티커 0개 · 종목이 안 겹친다"* 고 적었는데, 그것은 **티커 문자열**로 센 수다. 같은 회사가
한 갈래에는 `.KS`, 다른 갈래에는 `.KQ` 로 든 경우가 있다 — 종목코드로 다시 세니 **5종목**(holdout 1,464행 · main 330행 ·
원장 257,530행 기준). 같은 원인(계획 목록의 두 접미사)이고, 앞으로는 위 고침이 막는다. 옛 행은 지우지 않는다. 라운드 291 의
결론(날짜 미달로 순위 잣대를 못 연다)은 그대로라 판정은 안 바뀐다 — 그 문서에 정정을 붙였다. **홀드아웃으로 판정하려는
라운드는 종목코드로 다시 세고 겹치는 종목을 뺀다.**

## 4. 규칙으로 남기는 것

- **작업 전체가 성공이어도 단계 하나가 실패할 수 있다** — 저녁 작업의 '가장 나쁜 종료 코드'는 1 이었고, 그 한 줄이 그날치
  되받기를 말하고 있었다. 주기적인 일은 산출물(원장 행 수의 변화)로 센다(라운드 412·414).
- **증상을 재현한 가설은 원인을 재현한 것이 아니다** — 같은 환경에서 다시 돌려 확인하기 전에는 고쳤다고 적지 않는다.
- **열쇠를 고친 뒤에는 "한 실행 안"도 본다** — 완료 집합은 실행 시작에 한 번 읽히므로, 같은 열쇠가 계획 안에서 두 번
  생기는 길은 완료 판정이 못 막는다.
