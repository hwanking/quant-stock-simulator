# R222 — 실전 추천 추적: 같은 추천이 모델 버전마다 다시 동결됐다 (2026-09-04)

**상태**: 데이터 정직성 수정 · **판정·문턱 변화 없음** · 계산 파일 불변(§1).
행은 하나도 지우지 않았다(R197).

## 발단 — 3주 멈춘 루틴을 돌렸더니

화면 발밑에 이 줄이 있었다: *"실전 추천 추적 파이프라인: 동결 케이스 245건 ·
결과 확정 대기 245건 · 마지막 실행 2026-08-15"*. `OPERATIONS_ROUTINE` §2 가
**매 거래일** 돌리라는 루틴이 3주 서 있었고, 열린 245건 중 148건은 이미 20영업일
지평을 넘겨 채점 가능했다. DB 를 복사해 두고(`_probe/improvement.before.db`)
화면 버튼과 같은 명령(`scripts/run_daily_improvement.py`)을 돌렸다:

```
run=DAILY-… status=success added=218 resolved=169 errors=0
```

**추가 218 이 이상했다.** 이력 파일(`premarket_history.jsonl`)이 정확히 218줄
이다. 즉 **이력 전체가 새 케이스로 다시 들어갔다.**

## 기전 — 열쇠에 버전이 들어 있었다

`case_id = hash(ticker, signal_date, model_version, …)`. 모델 버전은 거의
날마다 바뀐다(오늘만 v2026.09.04.1). 그래서 파이프라인이 돌 때마다 지난 추천
전체가 "아직 없는 케이스"였다. 실행 이력이 그것을 이미 말하고 있었다 —
**08-15 에 같은 85건이 두 번**(v2026.08.12.1 · v2026.08.15.1) 들어갔다.

**R217 의 격자 밀림과 같은 모양이다** — 완료 판정의 열쇠가 잘못돼 옛 것이
새 것으로 세어진다. 추천의 정체는 **(종목, 기준일)** 이고 버전은 도장이다.

실측(`_probe/r222_dups.py`):

| | 값 |
|---|---:|
| 행 | 463 |
| 고유 (종목, 기준일) | **218** |
| 복사본 | **245 (53%)** |
| 복사본 수 분포 | 1벌 133 · 3벌 38 · 4벌 31 · 5벌 10 · **7벌 6** |
| 같은 쌍이 서로 다른 결과로 확정된 경우 | **0** |

마지막 줄이 중요하다 — 복사본은 같은 목표·손절·진입가라 같은 결과로 확정된다.
**빼도 정보는 하나도 사라지지 않는다.**

## 덤 — 7벌짜리는 회귀의 시험 픽스처였다

7벌인 여섯 쌍의 기준일이 **2099-01-01** 이었다. `test_pipeline_fixes.py` §61 이
*"실제 날짜와 충돌하지 않는 시험용 날짜"* 로 2099-01-01 리포트를 만들고, 그
이력 줄을 **사용자의 실제 이력 파일에 append 하고 남겨 뒀다**("이력은
append-only 로 남긴다"). 파이프라인이 그 줄을 읽어 버전마다 한 벌씩 실제
추적 DB 에 동결했다. R165 가 적은 *"검사가 사용자 자료를 바꾸고 있었다"* 의
그 자리다.

## 고침 — 열쇠·유입·표시·검사

1. **동결(`create_new_cases`)** — 이미 동결된 (종목, 기준일)은 어느 버전이든
   건너뛴다("이전 버전 케이스는 덮어쓰지 않는다"의 뜻이 그것이다). **미래
   기준일**은 있을 수 없으므로 건너뛴다. 둘 다 세어 찍는다(§3).
2. **기존 복사본 — 지우지 않고 표시** (`scripts/mark_tracker_duplicates.py` ·
   멱등 · 자체 백업): 같은 쌍의 **가장 먼저** 동결된 행(그때의 버전 도장이
   진실이다)을 남기고 뒤 복사본은 `dup_version`, 미래 기준일은 `void_fixture`.

   ```
   표시 전: failure 29 · open 294 · success 116 · unresolved 24   (463)
   표시 후: dup_version 239 · void_fixture 7 ·
            success 24 · failure 6 · unresolved 6 · open 181       (217 실제)
   실제 케이스 217 = 고유 (종목,기준일) 217 → 일치
   ```
3. **화면** — '동결 케이스'가 복사본·픽스처를 세지 않고, **뺀 수를 옆에 적는다**.
4. **§61** — 픽스처 이력을 임시 파일에 쓰고 실제 경로를 되돌린다. 검사('이력
   추가 저장')는 그대로, 부작용만 없앴다. 실제 이력의 2099 줄 수가 회귀 전후로
   같은지 §61 자신이 본다.

## 검사 — §239 (심어서 · 실제 DB 의 복사본 위에서)

임시 이력 세 줄(미래 · 이미 동결된 쌍 · 새 추천)을 실제 DB 의 **복사본**에
흘린다 → `added=1`, 건너뜀 "기존 1 · 미래 1" 이 찍힌다. 표시 스크립트를 두 번
돌려 두 번째는 할 일이 없는지(멱등), 표시 뒤 *실제 케이스 수 = 고유 쌍 수*
인지, 행이 하나도 안 줄었는지 본다. 실제 DB 에는 **미래 기준일로 열린 케이스가
없고** 항등식이 서는지 본다(값은 안 잠근다).

⚠️ **그 마지막 검사가 첫 판에 틀렸다** — SQLite 의 `date('now')` 는 **UTC** 라
한국 아침엔 어제다. 오늘 동결한 추천 5건이 '미래'로 잡혔다. 파이프라인이
쓰는 잣대(파이썬 로컬 `date.today()`)로 견준다 — 두 시계를 섞지 않는다.

## 무엇이 달라지나 · 안 달라지나

- 성과 지표(`refresh_metrics`)는 추적 DB 가 아니라 **리플레이 동봉본**을
  읽는다 — 복사본이 모델 성적을 부풀리지는 않았다. 부풀린 것은 화면의 케이스
  수와 파이프라인의 '확정' 수다.
- 오늘의 '확정 169' 도 복사본을 포함한 수다. 고유 기준으로는 **success 24 ·
  failure 6 · unresolved 6** — 36건이 확정됐다(hold·avoid 추천도 롱으로 가정해
  채점하는 것은 설계다).
- 루틴은 여전히 **자동이 아니다.** 화면 버튼이나 스크립트를 사람이 돌려야 한다
  — R196 이 리플레이 원장에서 적은 것과 같은 자리.

## 덤 셋 — 파이프라인이 이슈 하나를 닫았고, 회귀가 그것을 알렸다

오늘 실행의 `detect_issues` 가 `model|vb_gap`(검증-블라인드 괴리 감시)을
**닫았다** — 감지 규칙(≥10%p 면 열고 아니면 닫는다 · 기존 규칙)에 동봉본의
괴리 5.4%p(65.4 vs 60.0)가 못 미쳐서다. 그러자 회귀 §182 가 걸렸다:
*"연결한 이슈가 원장에 열려 있다 — 이슈가 닫히면 화면 문구도 사라져야 한다,
그때 이 검사가 알린다."* **설계한 대로 알린 것이다.** 화면의 버전 칩이 모델
축의 '다음에 보는 시점'을 그 이슈의 `next_review` 에서 읽고 있었다.

고침: 닫힌 이슈를 열린 과제로 말하지 않는다. 모델 축의 진짜 '다음에 보는
시점'은 이슈가 아니라 **전방 재평가일**이고, 그 날짜는 `forward_eval`(R78 이
만든 한 곳)에서만 읽는다 — 손으로 적지 않는다. §182 의 연결 목록도 현실에
맞췄다(§6). 주의 — 괴리가 5.4%p 로 닫혔다는 것이 "괴리가 없다"는 뜻은 아니다:
매수권 58+ 로 좁히면 7.6%p 이고 하락장에서는 34%p 다(R216). 감지 규칙은
전체 표본 기준이고, 그 사실은 모델 성적 화면이 따로 말한다.
