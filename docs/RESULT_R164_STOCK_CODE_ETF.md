# 라운드 164 — 못 찾던 종목의 원인은 하나였다: 코드를 `\d{6}` 으로만 읽었다

측정일 **2026-08-23** · 측정 전용 도구 `_probe/etf_code_probe.py` ·
`_probe/etf_nav_probe.py` · `_probe/etf_list_probe.py`

사용자가 두 종목을 못 찾았다.

| 이름 | 코드 | HTS 에서는 |
|---|---|---|
| SOL 팔란티어커버드콜OTM채권혼합 | `0040Y0` | 8,180원 · NAV괴리율 0.39% |
| ACE 미국빅테크7+데일리타겟커버드콜(합성) | `480020` | 10,290원 · NAV괴리율 0.49% |

## 2. 짐작하지 않고 쟀다

원인을 추측하기 쉬운 자리였다(“ETF 라서 제외되나 봅니다”). 그러지 않고
각 단계를 하나씩 통과시켜 봤다.

```
① 정규식      '0040Y0' 에서 \d{6}      → []            ← 여기서 이미 끝
② 정규화      normalize_code('0040Y0') → '000400'      ← 롯데손해보험
③ 이름 판별   is_fund_like(...)        → True          ← 여긴 멀쩡했다
④ 실제 조회   fetch_and_update(...)    → ticker=None, price=207,000
⑤ 검색 후보   search_naver(...)        → []
⑥ 네이버 원문 item/main?code=0040Y0    → 이름·현재가 정상 (8,180)
⑦ 검색 HTML   code= 표기               → 숫자 0개 · 영숫자 5개
```

**네이버는 멀쩡히 주고 있었다.** 못 읽은 것은 우리다.

## 3. 원인 셋 — 전부 '코드를 어떻게 읽나'였다

### ① KRX 문자 포함 코드를 이 저장소가 못 읽는다

KRX 는 요즘 문자가 섞인 6자리 단축코드를 발급한다. 네이버 ETF 목록
**1,161종목 중 296종목(25.5%)** 이 그 모양이다.

```
0167A0  0162Z0  0043B0  0193T0  0195S0  0072R0  0087F0 …
```

`\d{6}` 은 이것을 하나도 못 읽는다. 그리고 그 식이 **14군데**에 손으로
적혀 있었다.

### ② 못 읽는 데서 끝나지 않고 **남의 코드를 만들어 냈다**

```
normalize_code('0040Y0')        → '000400'   ← 롯데손해보험
normalize_code('ACE 미국빅테크7')  → '000007'
```

숫자만 뽑아 `zfill(6)` 하는 구현이었다. 관심종목·보유종목이 이 함수를
쓰므로 **다른 종목의 값이 내 줄에 붙을 수 있었다.** §3 이 금지한
'없는 값을 지어내기' 중에서도 나쁜 쪽이다 — 못 읽었다는 표시조차 없다.

같은 모양이 조회 함수에도 있었다. 코드를 못 찾으면

```python
return None, query, STOCK_METRICS_DB.get("005930.KS", {})
```

**삼성전자의 지표 뭉치**를 돌려주고 있었다. 실측에서 `0040Y0` 조회가
`price=207,000` 을 받아 왔다. 라운드 119 가 종목명에서 걷어낸
"실패하면 삼성전자" 가 여기 남아 있었다.

### ③ 이름에 괄호가 든 종목이 검색 목록에서 통째로 빠졌다

```python
for name, ticker in STOCK_NAME_MAP.items():
    if '(' in name: continue        # ← 별칭 키를 거르려던 줄
```

뜻은 *"'이름 (코드)' 별칭 키는 건너뛴다"* 였는데,
`ACE 미국빅테크7+데일리타겟커버드콜(합성)` 처럼 **이름 자체에 괄호가
있는 종목**까지 걸렀다.

게다가 이름 검색을 네이버 한 곳에만 맡기고 있었다 — 실측에서
`'미국빅테크7'` 검색이 **0건**이었는데 ETF 목록에는 8종목이 있다.

## 4. 고친 방식 — 호출부가 아니라 판별을 옮겼다

라운드 120c~e 에서 같은 결함을 호출부에서 **세 번** 고치고도 네 번째가
남았다. 그래서 이번에는 처음부터 한 곳으로 모았다.

**`stock_code.py`** — 단축코드를 읽는 유일한 자리.

- 식 `[0-9][0-9A-Z]{5}` · 문자가 섞이면 숫자 4자리 이상
- **새 규칙이 아니다.** `portfolio._read_code_token` ③ 가지가 이미 쓰고
  있었고 주석에 `ETF '0040Y0'` 을 예로 적어 두었다. OCR 경로에만 살아
  있던 그 규칙을 올렸을 뿐이다 (§2 — 채택된 규칙 재사용).
- 못 읽으면 **None**. 이름에서 숫자를 긁어모아 코드를 만들지 않는다.

호출부 여섯 곳(`portfolio.normalize_code` · `_read_code_token` ·
`search_naver_stocks_realtime` · `fetch_and_update_naver_realtime` 의 네
자리)이 전부 이것을 부른다.

## 5. 무엇을 **일부러 안 고쳤나** — 경계를 먼저 적는다

**유니버스·스캔·원장은 넓히지 않았다.** 시가총액 순위 스크래핑
(`fetch_market_listing`)과 관심종목 발굴(`market_attention`)은 지금도
숫자 6자리만 읽는다.

넓히면 ETF 가 추천 스캔 모집단에 들어가 **연구 표본이 바뀐다.**
라운드 129 가 같은 자리에서 참았다 — *"결과를 본 뒤에 잣대를 넓히지
않는다."* 넓히려면 새 사전등록이 필요하다.

이번에 넓힌 것은 **사용자가 직접 친 것을 찾아 주는 경로**뿐이다.
§201 이 이 경계를 검사로 못 박는다.

## 6. ETF 의 '적정가' — 만들지 않고 **받아 왔다**

사용자 요청은 *"ETF 도 적정가 살때말때"* 였다. 절반만 해 줄 수 있고,
그 사실을 화면이 그대로 적는다.

**못 하는 것 — 기업 적정가.** ETF 는 기업이 아니라 펀드라서 EPS·BPS·ROE
가 존재하지 않는다. 엔진은 이미 `is_fund_like` 로 펀더멘털 밸류에이션을
건너뛴다 — 그게 옳다. 라운드 44 주석이 경고한 대로 여기서 폴백이 걸리면
KODEX 200 에 '적정가 90,069원' 같은 근거 없는 값이 붙는다.

**할 수 있는 것 — NAV.** ETF 에는 원래부터 정답에 해당하는 값이 있다.
담고 있는 자산을 그날 값으로 평가한 순자산가치이고, **추정하는 값이
아니라 발표되는 값**이다.

지어내지 않았는지 확인한 것:

| 코드 | 현재가 | NAV | 괴리 | 사용자 HTS |
|---|---:|---:|---:|---:|
| 0040Y0 | 8,180 | 8,148 | **+0.39%** | 0.39% |
| 480020 | 10,290 | 10,240 | **+0.49%** | 0.49% |

괴리율 = (현재가 − NAV) ÷ NAV. 사용자 화면의 값과 **같다.**

갈래(고평가/정상/저평가) 기준은 **새로 만들지 않았다** — 이미 채택된
`VALUE_NEAR_PCT`(±3%)를 그대로 쓴다. 국내 ETF 의 괴리는 보통 이보다
훨씬 작아 대부분 '정상'으로 나오는데, 그것이 사실이다(잘 따라간다는
뜻). 좁은 기준을 감으로 만들어 없는 신호를 만들지 않았다.

## 7. 한계 — 먼저 적는다 (§3)

- **NAV 는 받은 그 시점의 값이다.** 그래서 저장소에 동봉하는 색인
  (`data/etf_index.json`)에는 **이름과 코드만** 넣었다. 낡은 NAV 를 오늘
  값처럼 보여 주지 않기 위해서다. NAV 는 살아 있는 조회에서만 나오고
  화면이 **받은 시각을 함께** 적는다. 못 받으면 '미수신'이라 쓴다.
- **ETF 목록은 네이버 스냅샷이다** — 상장폐지된 ETF 는 없다(생존 편향).
- **이 라운드는 우위를 만들지 않았다.** ETF 를 찾을 수 있게 됐을 뿐이다.
  이 엔진의 매수 신호에 비용 차감 뒤 재현되는 우위가 없다는 사실
  (라운드 148~160)은 ETF 라고 달라지지 않고, 화면이 그렇게 적는다.
- **NAV 괴리가 매수 신호라고 말하지 않았다.** 재지 않았기 때문이다.
  재려면 새 사전등록이 필요하다.

## 8. 곁들여 고친 것 — 사용자 요청 둘

- **최근 본 종목** — 종목 하나를 고르면 파이프라인이 몇 분 돈다. 그래서
  다시 보러 가는 일이 잦은데 매번 이름을 처음부터 쳐야 했다. 확정된
  종목만 20개까지 남긴다(오타·중간 입력은 안 남긴다). 무엇을 봤는지도
  개인 정보라 원격 접속에서는 파일에 쓰지 않는다 (§9).
- **관심종목 '메모' → '내 계획'** — 자유 메모는 다시 읽을 때 해석이
  필요한데 정작 보고 싶은 것은 매수·매도·보유 셋 중 하나였다.
  **이미 적어 둔 메모는 지우지 않는다** — 캡션이 그대로 보여 준다.
  이것은 사용자의 계획이지 엔진의 판정이 아니며 점수·적정가·판정에
  들어가지 않는다 (§9).

## 8b. 파다가 나온 것 — **눌러도 아무 일도 안 나는 버튼**

관심종목을 손보다 발견했다. 종목명 버튼 **두 곳**이 이렇게 돼 있었다.

```python
st.session_state['ticker_input'] = code
st.rerun()
```

**`ticker_input` 을 읽는 곳이 저장소 어디에도 없었다.** 사이드바 캡션은
*"이름을 누르면 그 종목을 봅니다"* 라고 적고 있었고, 눌러도 화면은
그대로였다. 회귀 3,490건은 내내 초록불이었다 — 렌더도 되고 예외도 없다.

검색어를 넘기는 길은 원래 하나다(`pending_search`). 뉴스 띠(`?pick=`)가
그 길을 쓰고 있었는데 관심종목만 자기 키를 새로 만들었고, 그 키에는
받는 쪽이 없었다. **경로가 둘이면 한쪽만 고친다는 §4 의 더 나쁜
판본** — 경로가 **영(零)** 이었다.

일반화해서 검사로 만들었다(§201 ⓜ): AST 로 `st.session_state['k'] = …`
쓰기를 모으고, 같은 파일에서 문자열 상수 `'k'` 의 **전체 등장 횟수**를
센다. `전체 == 쓰기` 면 아무도 안 읽는 키다.

돌려 보니 30개 중 **2개**가 걸렸다 — 거짓 경보는 0.

| 키 | 무엇이었나 |
|---|---|
| `ticker_input` | 관심종목 이름 버튼 2곳 (죽은 버튼) |
| `_last_analysis_sec` | *"다음 분석의 예상 시간을 알려주려고 기억해 둔다"* 고 적고 그 다음이 없었다 |

둘 다 고쳤다. 앞의 것은 이동 경로를 `_go_stock` 하나로 모았고, 뒤의
것은 **적어 둔 의도대로** 진행줄에 '지난번 N초'를 적게 했다(스캔
진행줄이 이미 쓰던 표현 그대로 — 새 문구를 만들지 않았다).

## 9. 검사 (§201)

- 종전 동작 11가지가 그대로인가 (고치면서 깨뜨리지 않았는가)
- 문자 포함 코드 5가지를 읽는가
- **이름에서 코드를 지어내지 않는가** — 6가지
- 조회·검색 함수 안에 `\d{6}` 이 되살아나면 걸린다 (AST 로 함수 본문만)
- **유니버스는 그대로인가** — 넓히면 걸린다
- 심어 두면 실제로 잡는가 (0건이 '못 봤다'가 아니게 · §110)
- 동봉 색인에 NAV·가격이 들어가면 걸린다
- NAV 한 줄이 받은 시각을 적는가 / 시각이 없으면 지어내지 않는가
- 새 모듈 둘이 §16·§77·§110 검사 대상으로 **유도**됐는가
- **쓰기만 하고 아무도 안 읽는 세션 키가 없는가** (죽은 버튼) —
  그리고 죽은 키를 심어 두면 실제로 잡는가

## 10. 회귀가 잡은 것 — 내 실수 둘

첫 실행에서 3건이 걸렸다(3,552건 중). 실행기가 *"검사 실패 — 재시도하지
않는다"* 로 자원 문제와 갈라 준 덕에 바로 원인으로 갔다.

**① §184 가 옛 구현을 요구하고 있었다.** `wl_mm_`(메모 입력칸)이 있어야
통과하는 검사였다. 메모를 '내 계획'으로 바꿨으니 당연히 걸린다.
검사를 **현실에 맞췄다**(§6) — 지키려는 것(*"사용자가 적는 칸은 셋뿐,
엔진 값 칸에는 입력 위젯이 없다"*)은 그대로 두고, 옛 칸이 **남아 있으면
실패**하는 검사를 하나 더 붙였다(값이 두 곳에서 오면 §4 위반이다).

**② 유도가 또 좁았다 — 세 번째다.** 새 모듈 둘이 *"검사 대상에 유도되지
않았다"* 고 걸렸다. 원인은 `reachable_modules()` 가 `git ls-files` 로
**추적 중인 파일만** 봤다는 것 —

> **새로 만든 파일은 커밋하기 전까지 §16·§77·§110 밖에 있다.**
> 그런데 검사가 가장 필요한 것이 새 파일이다.

라운드 114(손 목록 → 유도) · 라운드 120e(`from pkg import mod` 누락)에
이은 같은 모양의 세 번째다. `--others --exclude-standard` 를 더해 아직
`add` 하지 않은 파일도 보게 했고, gitignore 된 `_probe/`·`_archive/` 는
여전히 빠지는지 확인했다.

**35개 → 37개.** 라운드 120e 가 *"유도 결과의 개수를 찍으라"* 고 한
이유가 이것이다 — 숫자가 안 움직이면 그 창은 아직 닫혀 있다.
