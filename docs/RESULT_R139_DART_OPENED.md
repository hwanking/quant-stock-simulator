# DART 공시가 과거로 열린다 — 라운드 139 (수집 시작)

**라운드 124 의 "DART 미연동 · 수집 시작 + 12개월"이 틀렸다.**
`selectDate=YYYYMMDD` 를 붙이면 과거 하루가 그대로 열린다 — **2012년까지
확인했다.** API 키도 로그인도 필요 없다.

**이런 줄이 두 번째다.** 라운드 130 에서 네이버 수급이 같은 식으로
열렸고("6~12개월 기다려야" → 2013년까지 소급 가능), 이번이 두 번째다.

측정일 **2026-08-20**. 근거: `scripts/disclosure_recorder.py` ·
`.portfolio/disclosures_daily.jsonl`

```bash
C:/Python314/python.exe scripts/disclosure_recorder.py --days 20
C:/Python314/python.exe scripts/disclosure_recorder.py --report
```

**수집만 했다.** 점수·게이트·문턱을 바꾸지 않았고, 측정도 하지 않았다 —
사전등록 없이는 재지 않는다 (§2).

---

## 1. 무엇을 눌렀나

지금 코드(`market_attention.fetch_disclosures`)는 **당일**만 읽고 있었다.
과거 날짜를 붙여 봤다.

| 붙인 것 | 결과 |
|---|---|
| `selectDate=2026-08-13` (하이픈) | **0행** |
| `selectDate=20260813` (하이픈 없이) | **100행** |

형식 하나 차이였다.

## 2. 얼마나 과거까지 — **행마다 자기 접수번호로** 확인했다

| 요청 날짜 | 행 | 그 날짜 공시 |
|---|---:|---:|
| 2026-08-13 | 100 | **98%** |
| 2025-08-20 | 100 | 98% |
| 2023-08-21 | 100 | 97% |
| 2020-08-20 | 100 | 93% |
| 2016-08-19 | 100 | 98% |
| **2012-08-20** | 100 | **90%** |

페이지를 넘겨도 날짜가 유지된다 — 1·2·5·9·12페이지 합계 **497/500 (99%)**.

> ⚠️ **처음엔 내가 잘못된 것을 쟀다.** 페이지 전체에서 `rcpNo` 를 모아
> 최솟값을 봤더니 요청 날짜와 안 맞아 "불일치"로 찍혔다. 원인은
> **정정공시가 원본(옛 날짜) 접수번호를 함께 싣기** 때문이다.
> 행마다 그 행의 접수번호를 보도록 고쳤다. 남은 1~10% 가 그 정정건이고,
> **결함이 아니므로 그대로 기록한다**(`rcp_day` 필드).

## 3. 실제로 모아 봤다

```
2026-08-20  270건
2026-08-19  233건
2026-08-18  316건
2026-08-17    0건   ← 일요일
```

**819건 · 3일.** 파싱은 깨끗하다(태그 섞임 0/100).

## 4. 라운드 124 가 요구한 숫자를 냈다 — **"기타" 58%**

R124 §3.1 이 이렇게 적어 뒀다:

> 제목만으로 태깅하면 재현율이 낮다. **그 낮음을 측정해서 적는다** —
> 태깅 정확도를 모른 채 이벤트 통계를 내면 그 통계는 태깅 오류의
> 통계다.

이제 값이 있다 (819건):

| 유형 | 건수 | 비율 |
|---|---:|---:|
| **기타** | 473 | **57.8%** |
| 증자·CB·BW | 75 | 9.2% |
| IR·안내 | 72 | 8.8% |
| 실적 | 59 | 7.2% |
| 수주·공급계약 | 52 | 6.3% |
| 자사주·배당 | 37 | 4.5% |
| M&A·분할 | 30 | 3.7% |
| 투자·설비 | 16 | 2.0% |
| 인허가·임상 | 5 | 0.6% |

**지금 분류기는 공시 열 개 중 넉 개만 알아본다.**
이건 한계이지 결함이 아니고, 이벤트 연구를 열기 전에 **먼저 올려야 할
숫자**다. 58% 를 '기타'로 둔 채 이벤트 통계를 내면 그것은 태깅 오류의
통계다 — R124 가 경고한 그대로.

## 5. 수집 비용

하루 약 **300건 · 3~4페이지**(주말 제외). 원장 기간(2011~2026, 약
3,700거래일)이면 **약 1만 5천 요청 ≈ 3시간**이다.

수급(라운드 130)의 24만 요청·40시간에 비하면 **훨씬 싸다.**
공시는 하루 단위로 받고, 수급은 종목 단위로 받기 때문이다.

## 6. 다음 — 그리고 하지 않을 것

**할 것**
1. 수집을 이어 돌려 원장 기간을 채운다 (약 3시간)
2. **분류기를 먼저 고친다.** '기타' 58% 를 낮추지 않으면 어떤 이벤트
   통계도 태깅 오류에 묻힌다
3. 그 다음에야 사전등록을 쓴다 — 이벤트 창(1/3/5/10/20일 초과수익)은
   R124 §3.2 에 이미 적혀 있다

**하지 않을 것**
- 측정. 사전등록 없이 재지 않는다
- 운영 반영. R55·R57·R66 전방 동결(~2026-11-16)을 건드리지 않는다
- 원장의 mfe/mae 재사용. 그것은 **청산 봉까지만** 잰 값이라 이벤트 창에
  못 쓴다 (R124 §3.2 의 경고 · 이 저장소가 이미 겪은 함정)
