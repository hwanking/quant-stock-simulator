# 매일 어제 것을 복원하고 있었다 — 라운드 81

**클라우드 축적이 하루도 안 쌓이고 있었다.** 이틀 연속 원장이 182,359건에서
멈췄는데 아무 검사도 안 걸렸다.

---

## 1. 증상

| 실행 | 복원한 태그 | 시작 | 끝 |
|---|---|---:|---:|
| 31620468295 (8/12 17:00Z) | data-20260811 | 181,959 | 182,359 |
| 31643470614 (8/12 21:38Z) | data-20260811 | 181,959 | 182,359 |

두 실행 모두 **같은 곳에서 시작해 같은 곳에서 끝났다.** 400건씩 쌓았지만
다음 실행이 그것을 못 받았다. 전 단계 `success` 였고 스냅샷 가드도
통과했다 — 가드는 **줄었는지**만 보기 때문이다.

## 2. 원인 — `createdAt` 은 자산이 쓰인 시각이 아니다

복원 단계는 이렇게 골랐다:

```
sort_by(.createdAt) | last
```

그런데 릴리스의 `createdAt` 은 **처음 만든 시각**이고, `gh release upload
--clobber` 로 자산을 덮어써도 **바뀌지 않는다.** 실제 값:

| 태그 | createdAt | 자산 갱신 | 크기 |
|---|---|---|---:|
| data-20260812 | 2026-08-10T05:42:42Z | **2026-08-12T23:57:21Z** | 108.0MB |
| data-20260811 | 2026-08-10T05:42:42Z | 2026-08-11T10:42:06Z | 109.2MB |

**두 릴리스의 `createdAt` 이 초 단위까지 같다.** jq 의 `sort_by` 는 동률에서
입력 순서를 지키므로 `last` 가 `data-20260811` 을 집었다. 업로드는
`data-$(date -u +%Y%m%d)` = `data-20260812` 로 갔다. 읽는 곳과 쓰는 곳이
갈렸다.

## 3. 고침

**"언제 쓰였나"로 고른다.** 태그 이름 정렬로도 되지만, 어떤 이유로 옛
태그에 새 자산을 올리는 일이 생기면 또 틀린다.

```bash
gh api "repos/$GITHUB_REPOSITORY/releases" --paginate \
  --jq '.[] | select(.tag_name|startswith("data-"))
        | select([.assets[]|select(.name|startswith("research_data_"))]|length > 0)
        | "\([.assets[]|select(.name|startswith("research_data_"))|.updated_at]|max)\t\(.tag_name)"'
```

- 자산이 **실제로 쓰인 시각**(`assets[].updated_at`)의 최대값으로 정렬
- 자산이 없는 릴리스(업로드 전에 죽은 실행)는 **후보에서 뺀다**
- 후보 목록을 로그에 통째로 찍는다 — 무엇 중에 무엇을 골랐는지 보이게

## 4. 왜 오래 안 보였나 — 정체는 축소가 아니다

라운드 71c 에서 만든 스냅샷 가드는 **줄었는가**만 본다. 60,462 → 400 같은
사고는 잡지만, 181,959 → 181,959 는 정상으로 본다. 요약도 최종 숫자만
찍었다:

```
원장 행수: 182359      ← 어제도 오늘도 같은 숫자인데 초록불
```

→ `snapshot_guard --delta` 를 만들어 **복원 기준선 대비 증분**을 찍는다.
늘어난 것이 하나도 없으면 그렇게 적는다:

```
⚠ 늘어난 것이 하나도 없다. 계획이 다 찼다면 정상이지만, 남은 케이스가
  있는데 0 이면 축적이 멈춘 것이다 — 복원이 최신 스냅샷을 집었는지
  위 로그를 확인한다.
```

**실패로 만들지는 않는다.** 계획이 다 찬 날은 0 이 정상이다. 대신 눈에
띄게 적는다 — 0 을 '다 했다'로 쓰지 않는 것과 같은 원칙이다(§3).

## 5. 잃은 것 / 잃지 않은 것

- **데이터는 안 잃었다.** `data-20260812` 는 `data-20260811` 을 포함하고
  400건이 더 있다. 고친 뒤 첫 실행이 182,359 에서 시작한다
- **잃은 것은 시간이다.** 8/11 이후 실행들이 같은 400건을 반복했다.
  남은 계획이 51,847건이므로 하루 400건이면 130일이 걸린다 —
  전방 재평가(2026-11-16)까지 다 못 채운다. 그 자체는 문제가 아니다
  (전방 재평가는 전방 데이터로만 판정한다)

## 6. 이 사고가 말해 주는 것

가드는 **자기가 보도록 만들어진 실패만** 잡는다. 라운드 71c 는 축소를
겪고 축소 가드를 만들었고, 그래서 정체를 못 봤다. 다음에 축적 파이프라인을
고칠 때는 "무엇이 조용히 실패할 수 있나"를 먼저 묻는다.
