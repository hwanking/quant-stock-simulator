## 무슨 일이 있었나

라운드 196 이 *"리플레이 원장이 16일째 안 자란다"* 를 찾아냈다. 랩이
아직 도는지 확인하려고 **`calibration_lab.py --limit 5` 를 돌렸다.**

랩은 정상 종료했다. 그리고 **원장이 줄었다.**

```
채점 대상 가상 판정   184,764건
판정 완료 176,099 + 미결 7,688 = 183,787건 저장
원장 184,759 → 183,787   (−972)
```

로그는 성공으로 끝났고, **경고는 한 줄도 없었다.**

## 왜 줄었나 — 두 가지가 겹쳤다

`scripts/calibration_lab.py`:

```python
for r in rows:
    pdf = price_cache.get(r['ticker'])
    if pdf is None:
        try:
            pdf, _ = eng.generate_synthetic_bitemporal_data(...)
        except Exception:
            continue          # ① 시세를 못 받으면 그 종목의 **모든 케이스**가 사라진다
    ...
with open(graded_file, 'w', encoding='utf-8') as gf:   # ② 그리고 통째로 덮어쓴다
```

- **①** 채점 루프가 시세 실패를 `continue` 로 넘긴다. 그 종목의 케이스가
  통째로 빠진다.
- **②** 원장은 파생물이라 매 실행 **전체가 다시 쓰인다.**

그래서 **네트워크가 한 번 흔들리면 연구 표본이 영구히 작아진다.**
그날 다음(Daum) API 가 HTTP 500 을 냈고, 10종목 **977건**이 빠졌다.

같은 계열의 사고는 **이 저장소에 이미 두 번** 적혀 있었다
(`scripts/backup_research_data.py` 주석):

> 라운드 71c — … 클라우드는 매일 그 회차 400건만 가진 원장을 새로 만들어
> 좋은 스냅샷 위에 올린다. **실제로 60,462건 → 400건이 됐다.**
> 라운드 72 — 샤딩을 붙이고 정확한 이름만 적어 뒀다가 신규 121,497건이
> 통째로 백업에서 빠질 뻔했다.

두 번 다 **백업에 무엇을 넣을지**로 고쳤다. **덮어쓰기 자체는 그대로**
남아 있었다.

## 일시적 장애가 아니었다

## 고침 셋 — 문턱이 아니라 사유로 막는다

**① 빠진 것을 센다.** 종전에는 그 수가 어디에도 없었다.

```
⚠️ 채점에서 빠진 케이스 977건 — 시세 미수신 977건(10종목) · 채점 불가 0건
   시세를 못 받은 종목: 003410.KS, 005390.KS, 010620.KS, 015350.KS,
                        031440.KS, 042670.KS, 049770.KS, 082640.KS,
                        091990.KQ, 299900.KQ
```

**② 이어받는다.** 시세를 더는 못 받는 종목은 **종전 채점 행을 그대로
남긴다.** `carried_over: True` 를 찍어, 이번 실행에서 다시 채점되지
않았다는 사실을 분석이 볼 수 있게 한다(§3).

> **다시 못 재는 것과 없던 일로 하는 것은 다르다.**

통계(`calibration.json`)는 **새로 채점한 것만으로** 낸다 — 재현 가능한
것만 센다. 그래서 원장 행수와 `total_cases` 가 다를 수 있고, 그 차이를
`carried_over` · `ledger_rows` 로 **산출물에 적는다.**

```
calib: total_cases 183,792 · carried_over 977 · ledger_rows 184,769
```

**③ 줄어들면 안 덮어쓴다.** 문턱(몇 % 이상 줄면)을 감으로 고르지
않았다(§2) — **사유로** 막는다:

> 시세를 못 받아 빠진 케이스가 있고, 결과가 종전보다 작으면 덮어쓰지
> 않는다. 부분 결과는 `.partial` 에 두고, 빠진 종목 목록과 함께
> `exit 2` 로 멈춘다.

그리고 되살리는 도구를 남겼다 — `scripts/restore_graded_from_backup.py`
(미리보기가 기본, `--write` 로 적용).

## 곁들여 — 같은 실수를 오늘 **세 번** 했다. 그래서 검사로 막았다 (§226)

| 무엇 | 어디 | 정의는 |
|---|---|---|
| `_PATH_YIELD_COST_PCT` | 클래스 몸통에 두고 `self.` 없이 | (§222 가 잡는다) |
| `_sf151.ledger_rows()` | §55 · 3,198줄 | §151 · 10,634줄 |
| `_read148(...)` | §55 · 3,173줄 | §148 · 10,287줄 |

셋 다 **컴파일은 통과하고 실행에서 `NameError`** 다. 이 파일은 4,000건을
20분 돌리므로, 그런 오타 하나가 **20분을 통째로 버린다** — 오늘 그렇게
두 번 버렸다.

그래서 §226 을 넣었다: 모듈 본문을 **줄 순서대로** 훑으며 아직 안 묶인
이름을 즉시 읽는 자리를 AST 로 잡는다. 함수·람다·클래스 몸통은 안 본다
(나중에 호출된다).

**판별식이 또 세 번 좁았다** — 이 세션의 반복되는 모양이다:

| 시도 | 결과 | 무엇을 오탐했나 |
|---|---:|---|
| ① 그대로 | **3,124건** | `for k in xs: f(k)` 의 `k`, 컴프리헨션 변수 |
| ② 같은 문장 안 바인딩 제외 | 3건 | — |
| ③ `X if 'X' in dir() else Y` 방어 인식 | **0건** | 이 저장소가 스스로 막아 둔 세 자리 |

③ 은 발견이기도 하다 — **누군가 같은 함정을 밟고 자리마다 막아 둔
흔적**이 이미 셋 있었다. 검사가 없으니 자리마다 막을 수밖에 없었던 것이다.

심기 넷으로 확인한다: 심은 '정의 전 사용'을 잡는가 · 정상 순서를
오탐하지 않는가 · `for`·컴프리헨션 변수를 오탐하지 않는가 ·
`dir()` 방어를 오탐하지 않는가.

## 그리고 이건 내 잘못이다

원장은 사용자의 연구 자료다. 나는 **백업 없이** 그것을 다시 쓰는
스크립트를 돌렸고, 972건을 지웠다. 되살렸지만 그건 17일 전 백업이
남아 있었기 때문이다.

→ **연구 자료를 다시 쓰는 작업은, 그 작업이 줄일 수 있는지 먼저 본다.**
  `open(..., 'w')` 가 있는 산출물 갱신은 전부 이 부류다.
