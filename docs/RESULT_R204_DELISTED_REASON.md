# 라운드 204 — '못 받았다'가 아니라 '더는 없다'였다

측정: 2026-09-02 · 근거: `_probe/r204_dead_tickers.py` ·
`_probe/r204_html_probe.py` · `_probe/r204_all10.py` ·
`_probe/r204_reason_check.py`

## 물음

라운드 197 이 시세를 못 받는 10종목의 977건을 `carried_over` 로
보존했다. 남은 물음: **상장폐지인가, 코드 변경인가, 우리 결함인가.**
답에 따라 할 일이 다르다 — 상장폐지면 지금이 최선이고, 코드 변경이면
새 코드로 이으면 재채점이 살아나고, 결함이면 고치면 된다.

## 측정 — 싼 것부터 (§2-7)

**① 네이버 검색** (저장소가 이미 쓰는 경로 · §9): 10종목 중 **8종목이
이름으로 검색된다** — 쌍용C&E·신성통상·HD현대미포·신세계푸드·
HD현대인프라코어·동원F&B·동양생명·위지윅스튜디오. 얼핏 "아직
상장돼 있다"로 읽힌다.

**② 종목 페이지** (대조군 포함): 그런데 `item/main.naver?code=` 로
조회하면 **10종목 전부 종목 페이지가 없다** — 네이버가 **메인 페이지**를
돌려준다(제목에 종목명 없음 · `no_today` 없음 · `wrap_company` 없음).
대조군 삼성전자는 정상 페이지다.

| | 검색 자동완성 | 종목 페이지 |
|---|---|---|
| 잃은 10종목 | 8/10 나옴 | **0/10** |
| 삼성전자(대조군) | 나옴 | 정상 |

검색 색인은 사라진 종목의 이름을 한동안 유지하지만, 종목 페이지는
상장폐지·합병과 함께 사라진다. **10종목 전부 이 세계에서 더는 거래되지
않는 코드다.**

## 그러므로

- **엔진의 거부(0.0 → 제외)는 옳았다.** R188 이 넣은 미수신 센티넬이
  정확히 설계대로 동작했다.
- **`carried_over` 보존도 옳았다.** 다시 못 재는 것과 없던 일로 하는
  것은 다르다 — 그때는 받을 수 있었고 제대로 채점된 행이다.
- **재채점 복구는 불가능하다.** 이 코드로는 시세가 다시 오지 않는다.

## 남은 결함 — 문장이 거짓말을 했다

실패 메시지가 `현재가 수신 실패` 였다. **일시 장애처럼** 읽힌다 —
실제로 나부터 다음(Daum) API 의 HTTP 500 을 보고 네트워크를 의심했다.
라운드 165 가 적어 둔 그 함정 그대로다:

> 사유를 섞지 않는다. 예외 하나가 "코드를 못 읽었다"(우리 문제)와
> "시세를 못 받았다"(상대 문제)를 같은 문장으로 말하고 있었다.
> **그 문장 때문에 처음에 네이버를 의심했다.**

이번 것은 세 번째 갈래다 — "시세를 못 받았다"(일시)와 **"이 코드로는
다시 받을 수 없다"(구조)** 를 같은 문장으로 말하고 있었다.

## 고침

파서(`fetch_and_update_naver_realtime`)가 **종목 페이지 부재**를
`page_status: 'item_page_missing'` 으로 기록하고, 실패 지점
(`get_realtime_stock_price_triple_check`)이 사유를 가른다:

```
구조:  003410.KS: 네이버에 종목 페이지가 없습니다(메인으로 넘어감) —
       상장폐지·합병이면 이 코드로는 다시 받을 수 없습니다.
       시세 미수신과는 다른 사유입니다.
일시:  XXXXXX.KS: 현재가 수신 실패 — 분석에서 제외합니다.
```

**판정은 안 바뀐다** — 가격은 여전히 0.0(미수신 센티넬)이고 종목은
여전히 제외된다. 바뀌는 것은 문장과 기록뿐이다. 랩의 건너뜀 로그도
이 문장을 그대로 이어받으므로, 다음 사람은 네트워크를 의심하지 않는다.

"상장폐지로 보인다"고 **단정하지 않았다**(§3) — 우리가 아는 사실은
"종목 페이지가 없다(메인으로 넘어감)"까지다. 문장이 그 사실과 조건부
함의만 말한다.

## 검사 (§230)

**실행으로** 확인한다(§222 — 존재는 실행이 아니다). 심은 DB 항목이
실제 코드 경로를 지난다 — `sector` 가 있으면 네트워크 fetch 를 건너뛰는
기존 분기를 이용하므로 **네트워크 없이** 돈다:

- 심기 ① `page_status='item_page_missing'` → 구조적 사유 문장
- 심기 ② page_status 없음 → 종전 문장 그대로
- 둘 다 **여전히 예외**(판정 불변의 증거)
- 기록 키와 판정 키가 같은 이름인지 (`page_status`)

실전 확인(회귀 밖 · `_probe/r204_reason_check.py`): 003410 실조회가
구조적 사유 문장을 낸다 — 3/3.
