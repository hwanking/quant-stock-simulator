# 결과 R283 — 꼬리 검사가 판정하는 날이 수집한 날이 아니었다 (2026-09-13)

## 1. 계기 — R280 의 예산이 통했는지 보려다

라운드 280 이 작업 한도를 300 → 350분으로 올렸다. 그것이 통했는지 보려고 실행 이력을 열었다.
마지막 예약 실행(2026-09-11)은 **작업 300분 정각에 `cancelled`** 이었다.

먼저 든 생각은 *"고쳤는데 또 죽었다"* 였다. 아니었다 — 재 보니 그 실행은 **R280 병합보다 5시간
앞선다**:

| | 시각(UTC) |
|---|---|
| 예약 실행 생성 | 2026-09-11 **12:42:35** |
| R280 이 main 에 들어온 시각(9560e1a) | 2026-09-11 **17:49:02** |

예약 실행은 생성 시점의 기본 브랜치 워크플로를 쓰므로 그 실행에는 350분이 없었다.
**R280 의 예산은 아직 한 번도 시험되지 않았다** — 첫 시험은 다음 평일 실행이다.
(*"고친 것이 안 통했다"* 와 *"고친 것이 아직 안 돌았다"* 는 다른 말이다.)

## 2. 그 김에 본 것 — 예약이 언제 도는가

| 예약일 | 크론 지연(분) | 작업(분) | KST 시작 → 종료 | |
|---|---:|---:|---|---|
| 2026-08-13 | 77 | 111 | 08-13 18:16 → 20:07 | |
| 2026-08-18 | 42 | 143 | 08-18 17:41 → 20:04 | |
| 2026-08-26 | 50 | 136 | 08-26 17:50 → 20:05 | |
| **2026-08-27** | **659** | 122 | 08-28 03:58 → 06:00 | ← 여기서 바뀐다 |
| 2026-09-07 | 367 | 114 | 09-07 23:06 → **09-08 01:01** | 날짜 넘김 |
| 2026-09-08 | 284 | 136 | 09-08 21:44 → **09-09 00:00** | 날짜 넘김 |
| 2026-09-10 | 288 | 199 | 09-10 21:47 → **09-11 01:07** | 날짜 넘김 |
| 2026-09-11 | 283 | 402 | 09-11 21:42 → **09-12 04:25** | 날짜 넘김 |

워크플로와 이 저장소의 문서는 *"평일 08:00 UTC(17:00 KST)에 돈다"* 고 적는다. 8월까지는
42~77분 지연이라 그 말이 맞았다. **2026-08-27 부터 276~726분**으로 늘어 시작이
21:36~23:06 KST 다. 최근 예약 12회 중 **6회가 한국 날짜를 넘긴다.**

이 지연은 우리가 어쩔 수 있는 것이 아니다. **크론을 앞당기지 않았다** — 관측된 지연에 상수를
맞추는 것이고, 지연이 사라지면 마감 전에 도는 실행이 된다(§2).

## 3. 그런데 그것이 검사 둘을 망가뜨리고 있었다

수집(전방 판정 기록)은 작업 **맨 앞**에서 돌고(R253), 검사는 **맨 뒤**에서 돈다(R247).
날짜를 넘기면 **둘이 다른 날에 있다.** 두 검사 다 '오늘 = 이 프로세스의 지역 날짜'였다.

실제 기록부와 실제 휴장일 판정으로 **되돌려 봤다**(판별을 베끼지 않고 진짜 함수를 불렀다):

| 수집일(작업 시작 KST) | 검사가 본 날(작업 종료 KST) | 수집일 판정 | 검사 판정 |
|---|---|---|---|
| 2026-09-10 | 2026-09-11 | **실패** | 통과 |
| 2026-09-09 | 2026-09-10 | 실패 | 실패 |
| 2026-09-08 | 2026-09-09 | 실패 | 실패 |
| 2026-09-07 | 2026-09-08 | 통과 | **실패** |
| 2026-09-01 | 2026-09-02 | **실패** | 통과 |
| 2026-09-11 | 2026-09-12 | 통과 | 통과 |

**넘긴 6회 중 셋에서 판정이 뒤집힌다.** 그중 2026-09-10 이 뼈아프다 — 전방 기록부에 그날
행이 **0건**이고(아래 표) 그것이 R272 가 만들어진 바로 그 사건인데, 검사는 09-11 을 보고
**통과**를 냈을 것이다.

```
전방 기록부 420행 · 날짜 7일 (2026-08-14 ~ 2026-09-11) · 휴장일 날짜 0개
  08-14 60 · 08-18 60 · 09-02 60 · 09-03 60 · 09-04 60 · 09-07 60 · 09-11 60
```

**기록기 자신은 멀쩡하다** — 21:4x KST 에 시작하니 자정 전에 쓴다. 휴장일 행 0개가 그것을
말한다. 어긋난 것은 **검사가 무엇을 '오늘'이라 부르는가**뿐이다.

곁들여 방향도 둘이다:
- **월~목** 실행 → 다음 거래일을 물어 행이 없으니 **거짓 실패**
- **금** 실행 → 토요일을 물어 휴장일로 **조용히 통과**(그 주의 0건을 영영 못 잡는다)

## 4. 고침 — 판정일을 한 곳에서 유도한다

`scripts/trading_day.anchor_day()` — **마지막으로 정규장 마감이 지난 거래일**.

```
월 21:42 → 월      화 02:36 → 월      토 04:25 → 금
금 23:59 → 금      금 09:00 → 목(마감 전)      일 정오 → 금
```

- 마감 시각은 이미 채택된 상수 하나(`bitemporal_engine.MARKET_CLOSE` = 15:30)를 **부른다.**
  여기서 다시 적지 않는다(§2-6 · R192 의 '베낀 판별식'). 부르는 비용 0.69초.
- 휴장일 판정도 한 곳(`improvement.case_tracker`)을 부른다(R252).
- 못 유도하면 **None** — 몰래 '오늘'로 떨어지지 않고 부르는 쪽이 **미측정**으로 적는다(§3).
- 로그는 판정일과 지금을 갈라 적는다: *"판정일 2026-09-11 · … (이 검사가 도는 지금은
  2026-09-13 이다 — 넘겼다)"*.

**판정자가 둘이라 둘 다 옮겼다** — 전방 기록부 가드(R272)와 실행 기록 검사(R263). 한 곳만
고치면 R246 의 *"고침이 판정자 한 명에게만"* 이다. §296 이 둘이 **같은 함수 객체**를 부르는지
값으로 본다(글자 대조가 아니라 `is` · R195).

## 5. 실행 확인

```
scripts/trading_day.py      지금 2026-09-13 · 판정일 2026-09-11
전방 기록부 가드            판정일 2026-09-11 … 판정일 행 60건  →> 통과 (rc 0)
실행 기록 검사              판정일 2026-09-11 … 시작한 실행 기록이 없다 →> 실패 (rc 1)
```

두 번째의 rc 1 은 **참인 실패**다 — 09-11 클라우드 실행은 300분에 잘려 그 단계까지 못 갔고,
이 PC 에서도 그날 파이프라인을 돌리지 않았다. 종전 규칙이었다면 오늘(일요일)은 휴장일이라
**아무것도 안 재고 통과**했을 것이다.

## 6. 하지 않은 것

- **크론을 안 옮겼다.** 지연은 플랫폼 사정이고, 관측값에 맞춰 시각을 고르면 그것이 손으로
  고른 숫자다(§2). 지연이 사라지면 앞당긴 크론은 마감 전에 돈다.
- **기록기는 안 건드렸다.** 휴장일 행 0개로 멀쩡함을 확인했다 — 안 깨진 것을 고치지 않는다.
- R280 의 예산이 통하는지는 **다음 평일 실행이 증명한다.** 여기서 증명한 것은 "지난 실행이
  그 고침을 안 갖고 있었다"까지다.

## 7. 규칙으로 남기는 것

- **검사가 도는 시각과 재려는 사건의 시각이 다르면, '오늘'은 이름이 아니라 버그다.** 꼬리에
  둔 검사는(R247 이 그렇게 두라고 했다) 앞에서 일어난 일을 판정한다 — 그 사이에 날짜가
  바뀔 수 있다.
- **바깥 사정이 조용히 바뀌면 안 고친 코드가 틀려진다.** 여기서 바뀐 것은 우리 코드가 아니라
  예약 지연이다(42분 → 283분). 검사는 그대로인데 뜻이 달라졌다.
- **"고친 것이 안 통했다"와 "고친 것이 아직 안 돌았다"를 가른다.** 실행이 어느 커밋을 들고
  돌았는지 먼저 본다.
