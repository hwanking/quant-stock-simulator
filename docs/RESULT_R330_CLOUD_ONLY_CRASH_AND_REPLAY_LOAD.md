# 결과 R330 — 클라우드에서만 죽던 취약구간 지도 · 리플레이가 실시간 확인을 부르던 적재 (2026-09-17)

사용자: *"실행해 주고 못 다한 작업 계속 찾아서 해 주고 배포해 줘."* 못 다한 일 중 하나는 R311 이 남긴 물음이었다 —
*"다음 실행이 적재인지 채점인지 말하면 고칠 자리가 갈린다."* 2026-09-16 예약 실행 로그를 열었다(R272 의 길).

## 그날 실행 — 무엇이 됐고 무엇이 실패했나

27단계 중 **업로드까지 전부 지나갔고**(스냅샷 올리기 성공) 실패는 꼬리 검사 하나 — `관측 연구 신선도 검사`:

```
원장 252,329줄 · 허용 밀림 800줄
[FAIL] 취약구간 지도 (라운드 69) — 원장 251,528줄일 때 만듦 · 밀림 801줄 · made=2026-09-08
```

## ① 취약구간 지도는 클라우드에서 **한 번도** 돌지 못했다

같은 로그의 `FN/FP 연구·취약구간 지도` 단계에 트레이스백이 있었다:

```
FileNotFoundError: … /_probe/kospi_daily_cache.json
```

`weakness_map.py` 가 코스피 일봉을 `_probe/kospi_daily_cache.json` 에서 **직접** 읽는데, 그 파일은 gitignored `_probe/`
안에 있어 **이 PC 에만** 있고, 만드는 코드는 다른 연구 스크립트(`regime_moe_lab`) 한 곳뿐이다. 클라우드는 매번 여기서
죽었고 `|| true` 가 삼켰다(R250·R263 의 *"`|| true` 뒤의 침묵"*). 9월 8일 사람이 이 PC 에서 만든 파일이 동봉본으로 올라가
그 뒤로 **낡지 않은 것처럼** 보였고, 원장이 801줄 자란 날 허용치를 1줄 넘어 처음 드러났다. **돌지 않는 생성기는 원장이
멈춰 있는 동안에는 안 보인다.**

같은 방식으로 그 파일을 **직접 여는 연구 스크립트가 다섯 더** 있었다(`gen_case_layers` · `gen_hier_tables` ·
`hier_prob_lab` · `exit_regime_study` · `regime_moe_lab`). 그리고 이 PC 의 캐시는 **2026-08-07 에서 멈춰** 있었다.

고침 — 받는 곳을 한 곳으로(`scripts/kospi_index.py` · R120e):
- 국면 규칙은 `trade_plan.market_state` 그대로 · 봉 수 3,000 은 `regime_moe_lab` 이 쓰던 수(새 숫자 없음).
- 관측 산출물(`weakness_map`)은 **먼저 받고** 못 받으면 캐시, 둘 다 없으면 멈춘다(국면 없는 지도를 만들지 않는다 · §3).
- 재현이 목적인 연구 스크립트 다섯은 **캐시가 있으면 그대로**, 없을 때만 받는다(이 PC 의 재현 결과 불변).
- 지도가 지수 출처·마지막 날짜·국면 미기록 행수를 같이 적는다.

재현 검사(바꾸기 전에): 실시간 코스피 3,000봉과 캐시 3,000봉이 **겹치는 2,973일 종가 전부 같고**, 4상태 판정도 겹치는
2,908일 **전부 같다.** 실시간은 캐시 뒤 27일(~2026-09-16)을 더한다. 이 PC 에서 새로 만든 지도: 국면 미기록 **15행 / 98,822행**
(종전 파일은 12행 — 3,000봉 창이 앞으로 밀려 가장 오래된 2014년 몇 행이 빠진다 · 사실대로 적는다). 지도는 blind 를 빼므로
캐시가 8월에 멈춘 것은 이 지도의 국면 칸을 거의 안 바꿨다 — **결함의 본체는 클라우드에서 한 번도 안 돈 것**이다.

## ② 120분은 '적재'가 먹었다 — 그리고 적재가 필요 없는 확인을 부르고 있었다

R311 의 계기가 답했다:

```
[시간] 계획 루프 3,494초 — 종목 600개 시세 적재 (종목당 5.82초)
가상 판정 계획: 완료 251928건 · 남음 1건 (계획 251929건 · 이번 pool 종목 600개)
채점 대상 가상 판정: 251929건
##[error] … '케이스 축적 (기록만)' has timed out after 120 minutes.
```

계획 루프가 58분, 이어 채점이 나머지 62분을 쓰고 끝나지 못했다(`[시간] 채점` 줄이 없다). 채점은 원장 **전 종목(1,547)**의
일봉이 필요하므로 종목당 5.82초면 적재만 약 150분 — **이 단계는 예산 안에서 끝날 수가 없었다.**

왜 종목당 5.82초인가 — 적재 함수(`generate_synthetic_bitemporal_data`)가 일봉 **앞에 실시간 삼중 확인**(네이버 basic ·
다음 시세 · 재시도)을 부른다. 화면 분석에는 필요하다(재무 메타를 채운다 · R167 *먼저 채우고 나서 읽는다*). 그런데 **리플레이
계획은 기준일 달력만, 채점은 원시 일봉만** 쓴다. 이 PC 에서 차갑게 쟀다(30종목): 삼중 확인 **0.67초** · 일봉 요청 **0.18초**,
옛 적재 전체 **1.31초** → 일봉만 **0.14초**.

고침 — 일봉 수신을 `bitemporal_engine.fetch_daily_bars` 로 **글자 그대로** 떼어 내고(코드 판별 · 원천 봉 정제 · 수신 실패 사유가
같다), 적재 함수는 삼중 확인 뒤에 그것을 부른다(일봉 수신은 한 곳 · §4). 랩의 세 자리(계획 루프 · 전방 달력 · 채점)만 일봉만
받는다. 케이스를 만드는 `run_full_pipeline` 은 자기 적재를 따로 하므로 **판정 불변**.

재현 검사(바꾸기 전에 · HEAD 엔진 대 새 함수):
- 둘 다 받은 **19종목 전부 일봉이 같다**(DataFrame 동일).
- 클라우드 로그가 거부한 10종목 중 **8종목은 삼중 확인이 '종목 페이지 없음(상장폐지)'으로 거부했지만 일봉은 받을 수 있었다** —
  마지막 일봉 2021-12 ~ 2026-07, basic API 는 `409 StockConflict`. 진짜 상장폐지이고 판정이 옳다. 다만 **과거 일봉은 남아 있어**,
  그 종목들의 원장 **761행**은 R197 이래 `carried_over`(다시 못 잰 행)로 이어받던 것이 이제 다시 채점된다 —
  **761/761 이 저장된 채점과 같았다.** 그래서 원장 값은 안 바뀌고, 그 행들이 `carried_over` 표시를 벗고 통계(점수대 표 등)에
  다시 들어간다(R197 의 *"다시 못 잰 것은 통계에서 뺀다"* 가 풀리는 쪽 · `total_cases` 가 그만큼 는다).
- 나머지 2종목은 둘 다 일봉 수신 실패 — 사유 문장 글자까지 같다.

⚠️ **클라우드에서 얼마나 빨라지는지는 모른다.** 이 PC 는 9배였고 클라우드의 5.82초가 같은 비율로 줄지는 러너의 회선이 정한다.
**다음 실행의 `[시간] 계획 루프` · `[시간] 채점` 두 줄이 증명한다**(R259 의 그 문장). 채점이 예산 안에 끝나 `[시간] 채점` 줄이
찍히면 이 벽은 넘은 것이고, 원장이 실제로 자라는 것은 여전히 35일 잠금(R309 · 2026-10)이 정한다.

## 바꾸지 않은 것

판정·값·문턱·산식 · 원장 행 · 워크플로(순서·예산) · 화면. 계산부의 점수·게이트 코드는 열지 않았다 — 엔진에서는 일봉 수신
덩어리를 **옮기기만** 했다. 검사 §336(11건) · §202·§315 를 새 자리에 맞췄다(주석에 사유).
