# 라운드 445 — 남의 서버 오류 한 번이 그날 축적을 지웠다

2026-10-08 · 사용자: *"계속 진행해줘 남은 것도 찾아서 해줘."* 클라우드 실행 이력부터 열었다(R272 의 길).

## 무엇이 있었나

2026-10-07 예약 실행(37643284609 · 시작 00:21 KST · 1h35m)은 축적·검사 단계를 **전부** 통과했다. 원장 257,930 → 258,330,
전방 기록부에 판정일 10-07 행 60건, §9 zip 감사 통과, 축소 없음. 그리고 '새 스냅샷 올리기'에서 죽었다:

```
HTTP 500 (https://api.github.com/repos/…/releases)
release not found
```

릴리스 만들기가 GitHub API 의 **HTTP 500** 을 받았고, 뒤의 `|| gh release upload … --clobber` 는 릴리스가 없으니 실패했다.
러너가 내려가며 그날 것이 통째로 사라졌다 — 라운드 71c·247·253·280 에 이어 **다섯 번째 '쌓기는 쌓았는데 저장이 안 됐다'** 이고,
이번엔 예산도 순서도 아니고 **남의 서버 한 번**이었다.

## 되살린 것과 못 되살린 것

판정일은 '마지막으로 장이 끝난 거래일'(라운드 283)이라 이튿날 장이 끝나기 전까지는 여전히 10-07 이다. 그날 08:46 KST(장 전)에
이 PC 에서 **같은 기록기**(`scripts/forward_recorder.py --top 60` · 코드 불변)를 돌렸다 — 라운드 280 이 그날 안에 한 그 길이다.

| 무엇 | 결과 |
|---|---|
| 전방 기록부(fr-1) | 10-07 행 **60건** · 규약 거부 0 → 1,320건 |
| 교정본 그림자(sh-1) | 60줄 · 실패 0 |
| 재무 시점 보관 | 97줄(받은 응답 없음 1종목) |
| 잔여 호가 시점 보관 | 60줄 · 장 상태 **PREOPEN** |

클라우드 판과 다른 점을 적는다(같은 것으로 꾸미지 않는다 · §9):
- 판정은 같은 판정일·같은 일봉이다(엔진의 현재가는 판정일 봉의 종가 · 판정일 뒤 봉은 안 읽는다). 다만 돌린 시각이 00:21 이 아니라
  08:46 이라 **뉴스 수신분**은 그 사이 것이 섞일 수 있다.
- 잔여 호가는 클라우드라면 그날 밤(시간외 마감 뒤) 남은 호가였을 것이고, 이 판은 **이튿날 장 전(PREOPEN) 호가**다. 행에 받은 시각과
  장 상태가 같이 적혀 있어 가를 수 있다(라운드 342 가 그것을 남기게 했다).
- **못 되살린 것**: 그날 밤 클라우드의 뉴스 사건 4건 · 원장 +400(다음 실행들이 같은 계획을 다시 잡으므로 하루 늦을 뿐이다) ·
  클라우드 개선 DB 의 그날 변경(이 PC 의 DB 가 원본이다 · 라운드 415).

그리고 **이 10-07 행들은 이 PC 에만 있다** — 클라우드의 다음 실행은 마지막으로 올라간 10-06 판에서 시작하므로 10-07 을 모른다.

## 고친 것 셋 (순서·예산 불변)

**① 올리기를 다시 한다 · 끝내 못 올리면 실행 산출물로 남긴다.** 업로드 단계가 세 번까지 하고, 매번 릴리스가 **이미 생겼는지 먼저
본다**(500 이 나도 만들어졌을 수 있다 — 그러면 만들기 대신 올리기). 세 번 다 실패하면 실패로 끝나고(성공으로 꾸미지 않는다), 바로
다음 단계가 **§9 감사가 연 그 zip** 을 실행 산출물로 남긴다(사람이 받아 올릴 수 있게 · 그날 것은 그날만 만들 수 있다 · R253).

**② 첫머리 내려받기가 '못 읽었다'를 '없다'로 읽지 않는다.** 같은 모양을 찾다가 더 위험한 자리가 나왔다. 실행 첫머리의 릴리스 목록
읽기가 `|| true` 였다 — API 가 한 번 500 을 주면 후보가 **빈 것으로** 읽혀 *"이전 스냅샷 없음 — 빈 원장으로 시작"* 으로 갔다.
그러면 그날 끝에 **작은 스냅샷이 Latest 로 올라가고**(축소 가드는 복원 기준선이 0 이라 못 막는다) 다음 실행이 거기서 시작한다 —
원장 사슬이 통째로 끊긴다(라운드 245 보다 나쁜 모양). 목록 읽기와 내려받기를 몇 번 다시 하고, 끝내 못 하면 **빈 원장으로 가지
않고 멈춘다.** 목록을 **읽었는데** 후보가 없을 때만 빈 원장으로 시작한다(처음 도는 저장소). **없다와 못 읽었다는 다르다**(§3 · R284).

**③ 되받기가 이 PC 에만 있는 시점 기록을 지우지 않는다.** 되받기는 전방 기록부·그림자·시점 재무·잔여 호가를 **통째로 덮었다.**
오늘은 받은 쪽(1,260줄)이 이 PC(1,320줄)보다 짧아 축소 가드가 건너뛰지만, 클라우드가 다음 거래일 60줄을 더하는 날 **줄 수가
같아져** 덮이고 10-07 이 조용히 사라진다. 넷을 라운드 392 의 열쇠 합집합(종목 6자리, 날짜)에 넣었다 — 기록기가 이미 같은 열쇠로
멱등이다. 시점 보관·그림자는 종목을 `code` 로 적으므로 열쇠가 그것도 읽고, 날짜·종목이 없는 줄은 하나로 뭉치지 않고 '못 읽은 줄'로
남긴다. 실제 릴리스로 미리보기(쓰지 않음): 전방 기록부 *"받은 1,260 + 이 PC 에만 60 = 1,320"* · 그림자 180 + 60 · 시점 재무 546 + 97 ·
잔여 호가 540 + 60.

재시도 횟수(3)와 기다림(30·60초)은 판정 문턱이 아니라 운영 값이다 — 무엇을 막고 통과시키는지가 아니라 남의 서버를 몇 번 다시
부를지다(라운드 219 의 '한 번 재시도'와 같은 성격). 작업 한도(350분) 안에서 최대 몇 분이다.

## 시험 — 그리고 그 시험이 낸 사고

업로드·내려받기 단계를 워크플로 YAML 에서 그대로 꺼내 **가짜 `gh`·`sleep`** 으로 돌렸다(회귀 §431). 갈래:

| 갈래 | 옛 단계 | 새 단계 |
|---|---|---|
| 첫 만들기 500 · 릴리스 안 생김 (**10-07 의 모양**) | 실패 | 두 번째 만들기로 성공 |
| 500 인데 릴리스는 생김 | 성공 | 있는지 보고 올려 성공 |
| 계속 실패 | 실패 | 세 번 뒤 실패(마지막 뒤엔 안 기다림) |
| 목록 읽기 계속 실패 | **'빈 원장으로 시작' · 성공** | 세 번 읽고 멈춤 |
| 목록 한 번 실패 | — | 다음에 읽어 그 스냅샷을 받음 |
| 목록을 읽었는데 후보 없음 | — | 빈 원장으로 시작(허용) |
| 내려받기 계속 실패 | — | 멈춤 |

⚠️ **이 시뮬레이션의 첫 판이 진짜 `gh` 로 새서 실제 릴리스를 만들었다.** 가짜를 담은 폴더를 `PATH` 앞에 `C:/…` 꼴로 넣었는데
Git Bash 의 `PATH` 는 콜론으로 갈라 그 항목이 깨졌고, 진짜 `gh` 가 저장소에 `data-20261007`(제목 "t" · 2바이트 zip)을 만들어
**Latest** 가 됐다. 그대로 두면 그날 밤 클라우드 실행과 이 PC 의 저녁 되받기가 그것을 받는다(고르는 기준이 자산이 쓰인 시각이다 ·
라운드 81). '호출 0회인데 종료 코드 0' 이라는 결과가 단서였고, 약 1분 뒤 내 파일 이름·크기·내려받기 0회를 확인하고 태그와 함께
지웠다(다른 릴리스는 안 건드렸다 — 모든 호출이 같은 날짜 태그로 갔다). 그래서 시험은 **막힌 채로 시작한다**: 첫 줄에서 가짜가
잡혔는지 보고 아니면 99 로 멈추고, 토큰을 지우고 설정 폴더를 비우고 저장소를 없는 이름으로 두며, 임시 폴더는 `_probe/` 아래다.
그 막힘을 먼저 심어서 본다(가짜를 안 넣으면 99 · 호출 0). **밖으로 나가는 도구를 부르는 스크립트의 시험은 '안 새는가'부터 잰다.**
그리고 가짜가 처음엔 오류를 표준출력으로 내서 목록 파일에 `HTTP 500` 이 들어갔다 — 진짜 `gh` 는 표준오류로 낸다. 가짜를 실제와
같게 고쳤다(가짜가 실제와 다르면 시험이 다른 것을 잰다 · R320).
