# 결과 R343 — "그날로 미뤄진 진짜 비용"은 16초였다 · rs60 은 백필할 것이 아니다 (2026-09-21 · 문서 전용)

상태표 #10·#71 은 *"11-16 업황 축 재실행 전에 rs60 을 원장에 백필해 둬야 한다 · 그 비용이 그날로 미뤄져 있다 ·
비용 미셈"* 으로 서 있었다. 비용을 안 센 채 열흘 넘게 '큰 일'로 남아 있던 자리라 **세었다**(§2-7 — 싼 것부터).

## 잰 것 (2026-09-21 · 이 PC · 원장 읽기만 · 아무것도 안 씀)

rs60 은 `sector_cycle.proxy_momentum(그룹, as_of)` 가 내는 값이고 **종목이 아니라 (업종 그룹, 기준일)의 함수**다.
그래서 원장 행 수가 아니라 고유 쌍 수가 비용을 정한다.

| | |
|---|---:|
| 원장 | 252,729행 · 읽기 3.6초 |
| 업종 칸이 있는 행 | 120,163 (47.5%) |
| 고유 (그룹, 기준일) 쌍 | 11,634 · 그중 프록시에 연결된 쌍 **9,396** |
| 연결된 행 | **73,849** (원장의 29.2%) · 그룹 12개 |
| rs60 계산 | 9,396쌍 · **12.2초**(첫 호출의 프록시 시세 수신 포함) · 쌍당 1.3ms |
| rs60 이 안 나온 연결 행 | **0** (그룹별 가장 이른 기준일 2015-06-12 ~ 2015-08-11) |

**합쳐 약 16초다.** 118시간짜리 축적 재실행도, 수 시간짜리 백필도 아니다.

## 누출은 없는가 — 먼저 봤다

프록시는 미국 상장 ETF 라 한국 기준일 D 의 미국 봉은 **한국 장이 끝난 뒤** 닫힌다. 같은 날짜 봉을 쓰면 미래를
훔친다. `_upto` 는 `bisect_left` 로 **기준일 전날까지만** 남긴다(독스트링도 그렇게 적는다) — D 의 봉은 안 쓴다.

## 판정

- **원장에 rs60 칸을 백필하지 않는다.** 재실행하는 날 그 자리에서 16초에 만들어지는 값을 파일에 굳히면, 프록시
  구성이나 이력이 바뀐 날 **낡은 복사본**이 하나 더 생길 뿐이다(R282·R261 의 '두 벌').
- #10·#71 의 *"미뤄진 비용"* 은 **없었다** — 닫는다. 11-16 재실행은 사전등록 그대로 돌리면 된다.
- 남는 사실 하나: 연결된 행은 원장의 **29.2%** 다. 업종 칸이 있는 행이 47.5% 이고(종목 단위 채움은 업종 성적
  생성기 쪽의 일이지 원장 칸이 아니다 · R218) 그중 프록시에 묶인 그룹이 12개뿐이다. 재실행의 표본은 그 29.2% 이고
  **날짜 하한은 그 안에서 다시 센다**(R291 — 이득 상한은 잣대의 단위로).
