## 1. 재료부터 쟀다 — 있다

네이버 ETF 상세의 WiseReport 페이지가 구성종목을 **HTML 안에 그대로**
담고 있다.

```json
{"TRD_DT":"2026-08-21","AGMT_STK_CNT":6924.0,
 "STK_NM_KOR":"삼성전자","ETF_WEIGHT":35.37}
```

**1,161종목 전부 수집 성공 (100%)** · 592초. 코드는 없고 **이름만** 온다.

---

## 2. 산식 — 배수를 만들지 않는 형태

ETF 1주의 값은 구성종목 주가의 합이 아니다(설정단위·좌수가 낀다).
그 배수를 우리가 추정하면 **거기서 지어내기가 시작된다.** 그래서 비율로만 쓴다.

```
적정 NAV ÷ NAV = Σ w_i × (적정가_i ÷ 현재가_i) + w_기타 × 1
```

`w_기타`(채권·현금·파생·해외)는 **1 로 둔다** = *"그 몫은 가치 판단을
하지 않는다"*, 그리고 화면이 그 크기를 적는다.

## 5. **재다가 더 큰 것이 나왔다 — 지어낸 재무지표가 화면에 나가고 있었다**

첫 측정에서 리츠 ETF 가 **NAV 의 13.4배**로 나왔다. 이상값을 파고 들어가니
구성종목 여섯이 **정확히 같은 적정가 52,713.75원**을 받고 있었다.

```
SK리츠        현재 5,680 → 적정 52,714
롯데리츠       현재 3,920 → 적정 52,714   ← 같은 값
ESR켄달스퀘어리츠 현재 2,985 → 적정 52,714   ← 같은 값
한화리츠       현재 5,480 → 적정 52,714   ← 같은 값
```

원인은 `bitemporal_engine.generate_synthetic_bitemporal_data` 첫 줄이었다.

```python
meta = STOCK_METRICS_DB.get(symbol, {"eps": 5000.0, "bps": 45000.0,
                                     "pbr": 1.5, "roe": 12.0, ...})
```

`.get(symbol, 기본값)` 이라 **처음 보는 종목**은 통째로 저 리터럴을 받았다.
그리고 **DB 를 채우는 호출이 바로 다음 줄**이었다 — 읽고 나서 채우고
있었다. 순서만 뒤바뀐 것이다.

이 파일 `:787` 주석이 *"구버전은 eps=현재가×0.08, bps=현재가×0.7 …
재무지표를 통째로 지어내 DB에 넣었다"* 고 적어 둔 **그 결함의 생존자**다.

### 화면에 나가고 있었다 — 차가운 프로세스로 확인

```
COLD 330590.KS(롯데리츠) → 적정 52,713.75 · 신뢰 70.8 · CALIBRATED
     fund_df eps=None bps=45000.0 pbr=1.5 roe=12.0
COLD 395400.KS(SK리츠)   → 적정 52,713.75 · 신뢰 70.8 · CALIBRATED
```

**게시 재무가 없는 종목은 전부 같은 가짜 적정가를, 그것도 "CALIBRATED
신뢰도 70.8" 이라는 도장까지 붙여** 받고 있었다.

### 고침은 한 줄 — 먼저 채우고 나서 읽는다

```python
realtime_target_price, ... = self.get_realtime_stock_price_triple_check(symbol)
meta = STOCK_METRICS_DB.get(symbol) or STOCK_METRICS_DB.get(...) or {}
```

고친 뒤 (차가운 프로세스):

| 종목 | 전 | 후 |
|---|---|---|
| 롯데리츠 | 52,714 · CALIBRATED | **3,915 · CAUTION** |
| SK리츠 | 52,714 · CALIBRATED | **5,672 · CAUTION** |
| 삼성전자 | 270,365 · CALIBRATED | **270,365 · CALIBRATED** (그대로) |

그리고 룩스루 비율도 제자리로 왔다 — PLUS K리츠 **13.373 → 0.9965**,
WON 한국부동산TOP3플러스 **9.790 → 0.9719**. 2배 초과가 0개가 됐다.

### 왜 여태 못 봤나 — 이게 가장 중요하다

**한 프로세스에서 종목을 이어 돌리면 두 번째부터는 DB 가 데워져 정상값이
나온다.** 회귀도 앱도 늘 데워진 상태였다. 실제로 나도 처음에 데워진
프로브로 재서 *"엔진 재사용 때문"* 이라고 잘못 짚었다.

> **차가운 프로세스로 한 종목만** 돌려야 보인다.

그리고 애초에 이 결함을 잡은 것은 **이상값 하나**였다. 리츠 ETF 가
13배로 안 나왔으면 그대로 발표했을 것이다 — **같은 값이 여러 종목에
반복되면 그것이 신호다.**

## 7. 채택 — **표시 전용**

기준을 전부 통과했으므로 **148개 ETF** 에 룩스루 적정가를 화면에 낸다.
사전등록이 미리 못 박은 대로 **표시 전용**이다.

- 점수·게이트·추천에 **들어가지 않는다**
- **잰 날을 함께 적는다** (구성종목 적정가는 매일 바뀐다)
- 값을 못 낸 몫은 **1.0 으로 두었다**고 화면이 밝힌다
- **성과를 가르는지는 재지 않았다** — 원장에 ETF 가 없어 표본이 없다.
  라운드 44(업황)가 표시 전용으로 낸 자리와 같다

### 화면에 붙이다가 또 하나 잡았다 — NAV 가 두 값이었다

처음 붙였을 때 한 화면에 NAV 가 **둘** 나왔다.

```
ETF 순자산가치 (NAV)   107,601원          ← 방금 받은 값
담은 기업들의 가치로 …   NAV 110,197원의 1.086배   ← 잰 날의 값
```

산출물의 NAV 를 그대로 적었기 때문이다 — **§4 가 금지한 '한 화면이 스스로
모순되는' 그 모양**이다. 고쳤다: 산출물에서 가져오는 것은 **배수뿐**이고
NAV 는 화면이 방금 받은 것을 쓴다(배수는 무차원이라 곱하면 된다).
그리고 *"배수는 2026-08-24 에 잰 것이고 NAV 는 방금 받은 값입니다"* 라고
적는다.
