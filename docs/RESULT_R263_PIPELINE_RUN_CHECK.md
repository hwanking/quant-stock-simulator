# 결과 R263 — 일일 개선 파이프라인이 평일 26일 중 24일 흔적이 없다 · 침묵을 실패로 (2026-09-10)

전수조사(R252) 후보 #43. 라운드 250 이 *"`|| true` 단계가 9개인데 신선도 검사가 이름을 대는 산출물은
2개"* 라 셌고, 라운드 259 가 산출물 셋을 더했다. **실행 기록** 쪽은 아무도 안 봤다.

## 1. 실측 (2026-09-10 · `.portfolio/improvement.db` · 읽기 전용)

| | |
|---|---|
| `pipeline_runs` | **14행** · 고유 날짜 **6일** (08-02 · 08-08 · 08-15 · 09-03 · 09-06 · 09-07) |
| 08-02~09-07 평일 26일 | 기록 없음 **24일** (08-03~08-14 · 08-17~09-02 · 09-04) |
| 기록이 있는 시각 | 주말·저녁·UTC 새벽 — 사람이 이 PC 에서 돌린 시각이다 |
| 클라우드 단계 16 | `python scripts/run_daily_improvement.py \|\| true` — 매 평일 · 죽어도 초록불 |

파이프라인은 시작하자마자 `running` 행을 **커밋**한다(`improvement.daily_pipeline`). 그러므로 그날
행이 없다는 것은 **그날 시작조차 못 했다**는 뜻이다 — 09-02·09-04 는 워크플로가 "성공"한 날이다
(R245 의 실행 이력). 원인은 그날 단계 로그에 있는데 이 세션은 클라우드 로그를 못 읽었다(도구가
막혔다) — **원인은 다음 세션이 로그로 잡는다.** 이 라운드는 침묵을 붉게 만드는 것까지다.

## 2. 고침 — 검사 하나 · 워크플로 맨 뒤

- `scripts/pipeline_run_check.py`: 오늘(지역 날짜 · 워크플로는 `TZ=Asia/Seoul` · R222 의 UTC 함정)
  시작한 `pipeline_runs` 행이 있고 `success`/`partial_success` 로 끝났으면 통과. 없으면 **실패**.
  `running` 으로 남았으면 실패(죽은 채 남은 것). 휴장일은 판정하지 않는다(휴장일 판정은
  `case_tracker.is_non_trading_date` 한 곳 · R252). DB 를 못 읽으면 미측정(rc 2 · 통과 아님).
- 워크플로: 맨 뒤 "관측 연구 신선도 검사" 단계에 한 줄 — **업로드 뒤**라 실패해도 그날 축적은
  남는다(R247). `|| true` 는 안 붙인다.
- 단계 16 의 `|| true` 는 **그대로**다 — 축적을 인질로 잡지 않는다. 검사가 맨 뒤에서 말한다.

## 3. 잠근 것 — §277

빈 DB 실패 · 어제 행만 실패 · `running` 실패 · 오늘 `success` 통과 · 휴장일 rc 0 · DB 없음 rc 2 ·
워크플로 자리(업로드 뒤 · `|| true` 없음). 값은 안 잠근다.

## 4. 남은 것

- **왜 시작도 못 했나**는 안 밝혀졌다 — 09-02·09-04 실행의 단계 16 로그. 다음 클라우드 실행이
  이 검사에서 붉어지면 그 로그가 답이다.
- `pipeline_runs` 의 09-07 두 행(08:26Z · 10:13Z)이 클라우드 것인지 사람 것인지는 못 가렸다 —
  행에 실행 주체가 없다. 가르려면 `detail` 칸에 실행 환경을 적어야 한다(별도).
