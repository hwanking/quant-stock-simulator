## 0. 두 가지를 이어서 쟀다

라운드 358 이 **다음 라운드로** 미뤄 둔 것과, 그 라운드가 **안 적은** 것.

| | 라운드 358 이 남긴 말 | 오늘의 답 |
|---|---|---|
| ① | *"적자에 '산출 불가'를 주는 것은 게이트 변경이라 다음 라운드다"* | **안 만든다 — 이득 상한 0** |
| ② | `kind='gate'` 인데 전방 구간을 가르는 **날짜를 안 적었다**(R350 은 적었다) | **적을 필요가 없다 — 기록부가 행마다 찍는다** |

둘 다 **네트워크 0 · 새로 돌린 파이프라인 0** 으로 답했다. 먼저 클라우드 자료를
되받았다(원장 252,729 → **254,329** · 전방 기록부 660 → **900** ·
`fin_pit` 0 → **182** · `book_pit` 0 → **180** — 라운드 341·342 가 시작한 시점 보관이
클라우드에서 실제로 쌓이고 있다는 첫 증거다).

## 1. ① 막기만 하는 게이트의 상한은 "지금 통과하는 것"이다

'적자 → 산출 불가' 는 **후보를 더 넣지 않는다.** 막기만 한다. 그러면 이득 상한은
하나뿐이다 — **지금 통과하고 있는 것 중 적자가 몇이냐.** 두 곳에서 셌다.

**전방 기록부** (900행 · 거래일 15일 · 2026-08-14 ~ 09-23):

| 판정 | 행 |
|---|---:|
| HOLD | 890 |
| REDUCE | 10 |
| **매수** | **0** |

**개장 전 리포트** (94개 · 중앙 판정이 실린 후보 433개):

| | 수 |
|---|---:|
| **전 조건 통과** | **0** |
| 펀더멘털 밸류 검증을 통과한 후보 | 46 |
| 가장 자주 막은 조건 — 비용 차감 기대값 양수 | **432 / 433 (99.8%)** |
| 그다음 — 강제 차단 없음 / 신뢰도·전략품질 | 339 / 219 |

(라운드 316 이 87개 리포트·398후보에서 센 397/398 과 같은 모양이다 — 리포트가
94개·433후보로 자라도 **비율이 그대로**다.)

→ **이득 상한 = 0.** 출력이 이미 0 인 곳에서 막는 규칙을 더해도 막을 것이 없다.
밸류 검증을 통과한 46개조차 **전부 다른 조건에 걸려 있다**(전 조건 통과 0).

**그래서 안 만든다**(§2-7 의 *"상한이 작으면 그것만으로 접는다"*).

⚠️ **이것은 오늘 모집단에서의 상한이다**(§3). 라운드 317 의 벽(비용 차감 기대값이
중앙 −0.36%p 모자람)이 언젠가 열리면 그때 다시 센다 — **지금 안 만드는 이유는
"틀려서"가 아니라 "관측되는 것이 없어서"** 다.

그리고 **정직함 쪽은 이미 값을 치렀다** — 라운드 359 가 축 설명을 *"장부가 모델 N종"*
으로 좁히고 신뢰도 줄 아래 한 줄을 넣었다. 산출 불가로 바꾸는 것은 거기서 **정보를
빼는 것**이지 더 정직해지는 것이 아니다(장부가는 지어낸 값이 아니다).

## 2. 라운드 358 이 닿는 범위 — 전방 기록기 모집단에서 5종목

`fin_pit`(라운드 341 이 시작한 시점 재무)이 **그날 기록기가 본 종목의 재무**를 담으므로
네트워크 없이 셀 수 있다. **가장 최근 확정(추정 아님) 연도의 EPS**로 갈랐다:

| 날짜 | 종목 | EPS ≤ 0 | 못 읽음 |
|---|---:|---:|---:|
| 2026-09-21 | 60 | **5** | 0 |
| 2026-09-22 | 61 | **5** | 0 |
| 2026-09-23 | 61 | **5** | 0 |

그 5종목이 전방 기록부에서 받은 판정: **66행 전부 HOLD** — 라운드 358 **앞뒤 모두**.

⚠️ **대리 지표다**(§3). 라운드 358 의 깃발은 엔진이 받은 `eps`(TTM 계열)를 보고, 여기서
읽은 것은 **연간 발표치의 최근 확정 기간**이다. 둘은 다를 수 있으므로 이 수는 **상한**
이지 판정이 아니다.

## 3. ② 날짜를 안 적어도 되는 이유 — 기록부가 행마다 도장을 찍는다

라운드 350 은 비용을 바꾸며 *"11-16 은 그 날짜로 앞뒤를 가른다"* 를 손으로 적었다.
라운드 358 은 안 적었고, 그래서 오늘 그것이 구멍인지 봤다. **구멍이 아니다** —
전방 기록부는 행마다 `versions` 를 싣는다:

| 날짜 | 행마다 찍힌 model 버전 |
|---|---|
| 2026-09-16 | v2026.09.15.5 (60행) |
| 2026-09-17·18 | v2026.09.16.2 (각 60행) |
| 2026-09-21 | v2026.09.21.1 (60행) |
| 2026-09-22 | **v2026.09.22.0** (60행) — 라운드 350 의 비용 변경 |
| 2026-09-23 | **v2026.09.23.1** (60행) — 라운드 358+359 |

그리고 이것은 **약속으로 잠겨 있다** — `forward_registry.FIELDS` 에 `versions` 가 있고
`validate()` 가 *"필드가 아예 없다 / 비었다"* 를 잡으며, **쓰기 경로가 그 validate 를
실제로 부른다**(`forward_registry.py:246`). 즉 픽스처만 통과하는 계약이 아니라
**쌓이는 실제 행이 매번 검사를 받는다**(R195 의 *"존재는 실행이 아니다"* 를 먼저 확인했다).

→ **11-16 은 날짜가 아니라 버전으로 가를 수 있다.** 라운드 350 이 적은 날짜는 사람이
문서에서 읽기 위한 것이고, 기계적인 분할은 이미 되어 있다. **라운드 358 에 같은 줄을
더할 필요가 없다** — 없는 구멍을 메우려 검사를 더하지 않는다.

## 4. ⚠️ 내 판별식이 오늘만 **세 번** 틀렸다 — 전부 같은 모양

| # | 무엇을 물었나 | 나온 수 | 실제 |
|---|---|---|---|
| ① | `fin_pit` 행의 `eps`·`ticker` | *"적자 0 · EPS 못 읽음 **61**"* | 열쇠는 `code·date·items·periods` — EPS 는 `items['EPS'][기간키]` 안 |
| ② | 전방 기록부의 `core.bucket` | *"**? 900행** · 매수 0"* | 판정 칸은 **`action`** |
| ③ | 리포트 `premarket_report_*.json` | *"리포트 **0개**"* | `.portfolio/premarket_YYYY-MM-DD.json` — **94개** |

세 번 다 **"0 은 없다가 아니라 못 읽었다"**(R194)이고, 세 번 다 단서가 같았다 —
**전부가 한 칸에 몰린 수**(못 읽음 61 = 전체 · '?' 900 = 전체 · 0개). 네 번째도 있었다:
checks 의 이름 칸을 `label` 로 물어 *"가장 자주 막은 조건: **None 1312**"* 가 나왔다
(실제는 `name`). 그대로 적었으면 *"매수 판정 0행"* · *"밸류 통과 0"* 을 **측정했다고**
발표할 뻔했고 — 공교롭게도 **고친 뒤 매수 판정은 진짜로 0** 이다.
**맞는 답을 틀린 방법으로 얻는 것이 가장 위험하다.**

## 5. ⚠️ 회귀가 잡았다 — 자료를 되받으면 **동봉본이 그 순간 낡는다**

문서만 고친 라운드인데 전체 회귀가 **1건 실패**했다(R318 이 *"문서만 고친 라운드에서도
회귀는 돌린다"* 고 적은 바로 그 값어치다):

```
[FAIL] 동봉본이 실제보다 크게 뒤처지지 않는다 — 실제 254,329 · 동봉 252,729 · 차 1,600
```

**내 변경 때문이 아니다** — 이 라운드가 클라우드 자료를 되받아 원장이 +1,600 됐고,
배포가 읽는 `data/` 동봉본은 **2026-09-18 판** 그대로였다. 즉 **되받는 행위 자체가
동봉본을 낡게 만든다.** 라운드 282 가 고친 그 자리이고(*"온라인 화면은 문서와 다른 말을
하고 있었다"*), 그때 넣은 가드가 제 일을 했다.

`scripts/refresh_bundle.py --apply` 로 다시 만들었다 — **254,329건 전량** ·
gzip **32,320,889바이트**(평문 243,100,733 · 13.3%)로 저장소 파일 한도 100MB 안.
집계표 `total_cases` 도 254,329 로 같이 갱신된다.

⚠️ **그런데 거기서 멈추니 회귀가 다시 세 건을 잡았다** — 동봉본을 다시 만들자 그 도장이
2026-09-24 가 되고, 원장에서 파생되는 산출물 셋이 **09-23 판**(클라우드가 만든 것)이라
*"원장 파생물이 마지막 축적 뒤에 만들어졌다"* 에 걸렸다:

```
[FAIL] … sample_audit.json (2026-09-23)
[FAIL] … effective_n_icc.json (2026-09-23)
[FAIL] … sector_perf.json (2026-09-23)
```

라운드 259 가 *"생성기 셋 합쳐 약 30초"* 라 재 두었고 그대로였다 — 세 개를 다시 만들었다.

→ **자료를 되받는 라운드는 묶음이 넷이다**(둘이 아니다):
**① 되받기 → ② 동봉본 → ③ 원장 파생물 셋 → ④ 회귀.**
되받기만 하고 멈추면 배포 화면이 문서보다 1,600행 뒤에서 말하고(라운드 282 의 실측:
꼬리를 키우는 것으로는 안 맞고 **전량이어야 0.0%p**), 동봉본에서 멈추면 파생물이
낡은 채로 실린다. **한 번에 다 하지 않으면 회귀가 다음 단계를 가리킨다** — 오늘 실제로
두 번 그랬다(동봉본 1건 → 파생물 3건).

## 6. 바꾼 것

계산·판정·화면 코드는 **0**. 검사 0 · 버전 0.
바뀐 파일은 **자료**뿐이다 — 되받은 원장·기록부·관측 산출물(`data/`), 그 때문에 다시 만든
**배포 동봉본**, 그리고 그 도장 때문에 다시 만든 **원장 파생물 셋**.

이 라운드가 만든 것은 **수와 판단**이다:
① 만들지 않기로 한 게이트와 그 근거(이득 상한 0)
② 전방 구간 날짜를 안 적어도 되는 이유(기록부가 행마다 버전을 찍고 쓰기 경로가 검사한다)
③ **되받기 → 동봉본 → 원장 파생물 셋 → 회귀**가 한 묶음이라는 사실
④ 내 판별식이 같은 모양으로 네 번 틀렸다는 기록(전부가 한 칸에 몰린 수가 단서다)
