# 라운드 437 — 전방 기록기의 시계 경보가 자정 뒤마다 거짓이었다

2026-10-06 · 기록기 로그 문장만 · 기록·판정·문턱 불변 · 버전 없음

오늘 밤 할 일이 돌았는지 보려고 클라우드 실행 이력을 열었다. 10-05 예약 실행(시작 2026-10-06 01:58 KST)은 **데이터 오염 점검**에서
실패했는데 그것은 라운드 428 이 오늘 아침 고친 그 셈(같은 종목·날짜 복사본 2,499 → 2,500)이다. 그런데 같은 로그 맨 앞, 전방 판정
기록기가 이렇게 적었다:

    전방 판정 기록 — 기준일 2026-10-02 · 상위 60종목
      시계 2026-10-06 01:59 · 달력상 최근 거래일 2026-10-06
      ⚠ 기준일이 최근 거래일(2026-10-06)보다 뒤처졌다. 시계가 KST 가 아닐 수 있다 (러너는 UTC). … TZ 를 확인한다.
      오늘 이미 기록됨 — 판정원장 60종목 · 전방기록부 60종목 → 건너뛸 것 60종목
    기록 0건 · 실패 0건 / 대상 0종목

**기록은 옳았다** — 10-05 는 개천절(10-03 토) 대체공휴일이라 01:59 KST 에 마지막으로 장이 끝난 거래일은 10-02 이고, 그날 것은 이미
있었다. **경보가 거짓이었다.** 라운드 86 이 넣은 이 경보는 기준일을 *'달력상 최근 거래일'* — 오늘이 거래일이면 **장이 열리기 전이어도
오늘** — 과 견줬다. 예약 지연으로 기록기가 자정 뒤에 도는 날이면 매번 울리고, 원인을 엉뚱한 데(TZ)로 보낸다(라운드 294 의 *거짓
실패는 실패보다 나쁠 수 있다* — 이것은 경고라 작업을 멈추진 않았지만 로그를 읽는 사람을 잘못 보낸다).

고침 — `scripts/forward_recorder.clock_notes(t_ref, now)` 하나:
- 라운드 86 이 잡으려던 원인은 **시계의 UTC 오프셋**이다 — 그것을 직접 본다(+09:00 이 아니면 경고).
- 기준일은 **마지막으로 정규장이 끝난 거래일**(`scripts.trading_day.anchor_day` · 라운드 283 의 판정일 · 같은 휴장일 표·마감 시각)과
  견준다. 못 구하면 견주지 않는다고 적는다(§3).
- 머리 줄은 시계(오프셋 포함)와 그 판정일을 같이 찍는다.

심은 시계 넷: 10-06 01:59 KST · 기준일 10-02 → **조용** · 10-06 17:00 KST · 기준일 10-06 → 조용 · 08-13 08:00 **UTC** 시계(라운드 86 의
사고) → TZ 경고 · 10-06 17:00 KST 인데 기준일 10-02 → 밀림 경고. 회귀 §141 의 글자 잠금 둘을 이 동작으로 옮겼다.

확인만 — 오늘 17:00 이 PC 저녁 작업은 네 단계 전부 종료 0(되받기는 공개 HTTPS 길 · 관심종목 59행 재측정 · 실패 0). 클라우드의 10-06
실행은 아직 생성 전이다(예약 지연).
